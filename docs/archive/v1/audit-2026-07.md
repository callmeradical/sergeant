# Sergeant — System Audit, July 2026

**Scope:** `bin/`, `_sgt-*.sh` shared libs, schema, skills, and docs.  
**Axes:** Simplicity, Elegance, Correctness, Performance.  
**Method:** Full source read of all 25 `bin/` scripts and supporting files.

---

## Executive summary

The core dispatch / worker lifecycle machinery is sound and the safety
properties around intent, pane identity, and response acknowledgement are
real and tested. The correctness problems that exist are in the seams between
scripts — rollback gaps, race windows, a permanently-deferred prototype — not
in the core protocol.

The bloat hunch is correct, but it is concentrated rather than diffuse:

- **One heredoc** in `sgt-dispatch` accounts for most of the apparent size.
  The ~200-line worker brief is embedded inline and should be a standalone
  template.
- **Two heavyweight scripts** (`sgt-cleanup`, `sgt-respond`) contain
  complexity that is justified but needs better factoring into the shared lib.
- **Two scripts** (`wiki-daily-digest`, `oc-inject`) do not belong in `bin/`
  under the current design.
- **Scattered inline Python** (four invocation styles across seven scripts)
  should be standardised or promoted to a helper.

Fix those four concerns and the codebase shrinks considerably without
touching any protocol logic.

## 2. Simplicity

### S-1 ⚡ The worker brief is a 200-line heredoc inside `sgt-dispatch`

`sgt-dispatch` is 41 KB. The single largest contributor is the `.sergeant-brief.md`
heredoc that runs from the `cat > "$worktree_path/.sergeant-brief.md" << BRIEF_EOF`
line to `BRIEF_EOF` — roughly 200 lines of mission, protocol, and gate
instructions that change rarely.

Only a handful of values are interpolated: `$TASK_ID`, `$PROJECT`, `$REPO`,
`$BRANCH`, `$worktree_path`, `$repo_task_dir`, `$INTENT_REVISION`,
`$REPO_TD_TASK_ID`, `$td_section`, `$deps_section`, `$merged`,
`$review_axis_label`, `$accessibility_axis_markdown`.

**Recommended fix:** Extract to `templates/worker-brief.md` with `{{PLACEHOLDER}}`
tokens and render with a small `_sgt_render_template` helper (pure bash or
`envsubst`). The dispatch script drops from ~41 KB to ~25 KB. Brief content
becomes independently editable and diff-readable.

### S-2 ⚡ `sgt-cleanup` has 14 private functions and no shared benefit

`sgt-cleanup` defines these all-local helpers:
`_worktree_cwd_pids`, `_process_tree_records`, `_recorded_tree_pids`,
`_live_recorded_tree_pids`, `_terminate_pids`, `_process_group_pids`,
`_terminate_process_group`, `_stop_local_worker`,
`_stop_recorded_validation_group`, `_stop_validation_pane`,
`_stage_worker_evidence`, `_remove_worker_evidence`,
`_restore_worker_evidence`, `_record_cleanup_phase`.

`sgt-validate` independently re-defines `_worktree_cwd_pids` and
`_process_group_pids` — exact duplicates. Both sets of definitions exist
because the lib does not own process-management helpers.

**Recommended fix:** Promote `_worktree_cwd_pids`, `_process_group_pids`,
`_terminate_pids`, and `_terminate_process_group` into `_sgt-lib.sh`.
The termination logic in `_stop_local_worker` and `_stop_validation_pane`
is cleanup-specific and can stay local, but it becomes shorter when it calls
lib helpers.

### S-3 `wiki-daily-digest` does not belong in `bin/`

`wiki-daily-digest` is a personal productivity tool: it queries SQLite
databases from OpenCode, Goose, and Claude, calls the Anthropic API, and
writes a daily digest to `~/wiki/sessions/`. It does not touch any fleet
state, does not follow the `sgt-*` naming convention, and has no relation to
multi-repo dispatch coordination.

It lives in `bin/` because it is convenient to have it on `PATH`, not because
it is architecturally part of Sergeant. The `mise install` task symlinks it
alongside the `sgt-*` scripts.

**Recommended fix:** Move to its own repo or to `~/.local/bin/` directly.
If it must stay here, put it in a `tools/` subdirectory and exclude it from
the main README toolbelt table.

### S-4 `oc-inject` is a labelled prototype with no exit condition

The first comment in `oc-inject` reads:

```
# DELETE when prototype question is answered.
```

No issue number, no question, no timeline. The script is 4.5 KB of
non-trivial polling logic, it is symlinked by `mise install`, and it is
referenced by `sgt-notify`. If the prototype question has been answered,
delete it. If not, open a tracking issue and set a deadline.

### S-5 `_sgt_td_supported_version_output` is 80 lines for version matching

`_sgt-lib.sh` contains an 80-line function that parses `td --version` output,
handling both the one-line form and a four-line "update available" form. It
validates every field with separate regex patterns and cross-checks version
components.

This level of defensive parsing is appropriate if `td` frequently ships
output-format changes that have broken callers. If that history does not
exist, a simpler approach works:

```bash
_require_marcus_td() {
  command -v td &>/dev/null || _die "td is required …"
  td create --help 2>&1 | grep -q -- '--work-dir' || \
    _die "Unsupported td: requires --work-dir support"
}
```

The version-format parser has no tests that exercise the four-line branch.
If it is kept, it needs test coverage.

### S-6 `sgt-treehouse-init` is too thin to justify a separate file

At 80 lines (half of which are boilerplate shebang, sourcing, arg parsing,
and loop scaffold), `sgt-treehouse-init` does one thing: loop repos and call
`treehouse init` if `treehouse.toml` is absent. This could be a subcommand
of `sgt-sync` (`--treehouse`) or a short `[tasks.treehouse-init]` entry in
`mise.toml`.

## 3. Elegance

### E-1 `_die` is re-defined in `sgt-respond` after being sourced from lib

`sgt-respond` sources `_sgt-lib.sh` and then immediately re-defines `_die`:

```bash
source "$SCRIPT_DIR/_sgt-lib.sh"
…
_die() { echo "ERROR: $*" >&2; exit 1; }
```

The lib definition is identical. The redefinition is a no-op and confuses
readers into thinking there is a meaningful override. Delete the local copy.

### E-2 Four Python invocation styles across seven scripts

Scripts invoke Python in these distinct forms:

```bash
python3 -c 'single line'                          # sgt-dispatch
python3 - arg1 <<'PY'                             # sgt-td-create
  multiline
PY
python3 <<'PYEOF'                                 # wiki-daily-digest
  multiline
PYEOF
REPO_NAME="$x" "$GRAPHIFY_PYTHON" - <<'PY'        # sgt-graphify
  uses os.environ
PY
```

There is no rule governing which form is used where. The env-var injection
style exists only in `sgt-graphify` and forces Python to reach into the
environment for values that could be arguments.

**Recommended fix:** Adopt one style — `python3 - "$arg1" "$arg2" <<'PY'`
— where arguments are positional (`sys.argv`), the script is a heredoc, and
no environment injection is needed. Apply consistently.

### E-3 `sgt-watch` carries its own `_pane_is_supervisor` alongside a migration path

`sgt-watch` defines `_pane_is_supervisor` that first tries
`_sgt_pane_identity_matches` (from lib) but, on failure, falls back to a
longer manual comparison that writes a `pane_identity_migration` marker. This
migration-aware version is unique to `sgt-watch`.

The migration was presumably added when `pane_identity` files were introduced.
If all active fleet states now have `pane_identity` files, the fallback
branch is dead code. Verify, then remove the migration path and collapse
`_pane_is_supervisor` to a one-liner calling the lib function.

### E-4 Review axis heuristic concatenates all prose into one regex target

In `sgt-dispatch`, UI/accessibility review detection does this:

```bash
review_context="$(printf '%s %s %s %s %s' \
  "$BRIEF" "$repo_role" "$repo_group" "$group_description" "$merged" \
  | tr '[:upper:]' '[:lower:]')"
if [[ "$review_context" =~ (^|[^[:alnum:]])(ui|frontend|...)([^[:alnum:]]|$) ]]; then
```

A project YAML config field such as `review_axes: [standards, spec,
accessibility]` or `role: ui` on a group would make this explicit, testable,
and user-controllable. The heuristic works for simple cases but silently
misclassifies when "frontend" appears in instructions for a non-UI repo.

### E-5 The O(n) `yq`-per-field repo lookup is repeated in five scripts

`sgt-dispatch`, `sgt-td-create`, `sgt-context`, `sgt-status`, and
`sgt-sync` all use this pattern:

```bash
for ((i=0; i<repo_count; i++)); do
  n="$(yq ".repos[$i].name" "$CONFIG_FILE")"
  [[ "$n" == "$rname" ]] && break
done
raw_path="$(yq ".repos[$i].path" "$CONFIG_FILE")"
role="$(yq ".repos[$i].role // \"\"" "$CONFIG_FILE")"
# … 5-8 more yq calls per repo …
```

This issues one subprocess per field per repo. `sgt-td-list` already uses
the correct approach: `yq ".repos[] | select(.name == \"$rname\") | .path"`.

A lib helper that emits all fields for a repo as a single JSON blob (one `yq`
call per repo) would eliminate dozens of subprocess spawns and make the
lookup logic appear in one place.

### E-6 `sgt-graphify`'s `_require_python_runtime` reads graphify's shebang

```bash
graphify_bin="$(command -v graphify 2>/dev/null || true)"
if [[ -n "$graphify_bin" && -r "$graphify_bin" ]]; then
  IFS= read -r shebang < "$graphify_bin" || true
  if [[ "$shebang" == '#!'* ]]; then
    read -r -a words <<< "${shebang#\#!}"
    …
```

This introspects graphify's installation to find its Python interpreter so
that source rewriting uses the "same runtime." If graphify is a compiled
binary this parse produces nothing and the fallback (`python3`) is used
anyway. Just use `python3` and document the requirement. The current approach
adds 40 lines for an edge case that has no test.

## 4. Correctness

### C-1 🔴 TD task rollback does not cover worktree-phase failures

`sgt-dispatch` creates TD tasks for all target repos upfront via
`sgt-td-create`, then enters the per-repo worktree loop. Inside the loop, if
worktree creation fails for repo N (e.g., git fails), `_die` is called. At
that point:

- TD tasks for repos 1..N are already created and **not rolled back**.
- `repo_task_dir` for the failed repo may have been partially populated.
- The fleet state for repos 1..N-1 is `dispatched` with no matching process.

`_rollback_generated_td_tasks` is defined but is only called during the
*creation* phase (inside `sgt-td-create`), not after a worktree failure.

**Fix:** Accumulate successfully-dispatched repos and add a cleanup trap
around the dispatch loop that rolls back TD tasks and removes orphaned fleet
state directories if the loop exits with an error.

### C-2 🔴 `sgt-watch --sync` can false-orphan a worker in the `dispatched` window

In `_sync_task`:

```bash
case "$wt_status" in
  in_progress|dispatched)
    if [[ -n "$pane" ]] && ! _pane_is_supervisor "$pane" "$repo_dir"; then
      printf 'orphaned\n' > "$worktree/.sergeant-status"
```

`dispatched` is the initial status written by `sgt-dispatch` before the
worker has started. The interactive worker writes `in_progress` to fleet
state only after `sgt-interactive-worker` launches and calls `_sync_state`.
If `sgt-watch --sync` runs in this window — which is seconds wide — it
declares the worker orphaned because the pane is not yet the supervisor
identity.

**Fix:** Do not treat `dispatched` status the same as `in_progress` when
checking pane liveness. A `dispatched` repo is expected to have no confirmed
pane identity yet; skip the orphan check until status advances to
`in_progress`.

### C-3 🟡 `_migrate_legacy_response_state` in `sgt-respond` is undated technical debt

This ~100-line function in `sgt-respond` exists to backfill fleet state
fields (`worktree_git_pointer`, `worktree_git_dir`, `intent_revision`) that
were added after initial deployment. It runs every time `sgt-respond` is
called on a task that is missing these fields.

There is no comment stating when the migration was added, what schema version
it migrates from, or when it is safe to remove. Any fleet state created before
the migration was introduced will have been migrated by now if it has been
touched. Fleet state that has never been touched is stale.

**Fix:** Add a comment with the date and the schema version. Schedule removal
after a stated date (e.g., "remove after 2026-Q4, all active fleet state
post-migration").

### C-4 🟡 `_sgt_detect_agent` defaults unconditionally to `opencode`

```bash
_sgt_detect_agent() {
  if [[ -n "${SERGEANT_AGENT:-}" ]]; then echo "$SERGEANT_AGENT"
  elif [[ -n "${OPENCODE:-}" || -n "${OPENCODE_PID:-}" ]]; then echo "opencode"
  elif [[ -n "${CLAUDE_CODE_SESSION_ID:-}" … ]]; then echo "claude"
  else echo "opencode"   # ← always opencode if no env vars match
  fi
}
```

A user running only Goose who has not set `SERGEANT_AGENT` will see
`opencode: command not found` at dispatch time, which is confusing. The
default should be `""` (empty) and `_require_interactive_agent` should detect
the absence and print a useful install hint.

### C-5 🟡 No validation that project YAML `name` matches the filename

`sgt-list`, `sgt-context`, and `sgt-dispatch` all read `name` from the YAML,
but none verify it equals the project argument derived from the filename. A
project file named `smith.yaml` with `name: jones` will silently emit
confusing output.

**Fix:** Add a check in `sgt-context` (the canonical context loader):

```bash
yaml_name="$(yq '.name' "$CONFIG_FILE")"
[[ "$yaml_name" == "$PROJECT" ]] || \
  _die "Project name mismatch: file is $PROJECT.yaml but name: $yaml_name"
```

### C-6 🟡 Branch name is placed into tmux `WINDOW_NAME` without sanitising for tmux

`WINDOW_NAME="${STAGE}-${rname}-${TASK_ID}"` and the branch-derived
`TASK_ID` (from the brief) can contain characters that tmux interprets
specially in window names (e.g., `.`, `:`, `%`). The slug derivation already
filters to `a-z0-9-` so in practice the risk is low, but the stage name
comes from user input (`--stage`) and is only validated against
`^[a-z0-9]+(-[a-z0-9]+)*$`, which does not cover all tmux-special chars.

### C-7 🟡 `wiki-daily-digest` defaults to `claude-haiku-4-5`

```bash
MODEL="${WIKI_DIGEST_MODEL:-claude-haiku-4-5}"
```

The current Anthropic model identifiers follow `claude-3-5-haiku-20241022`
or `claude-haiku-3-5` style. `claude-haiku-4-5` does not match any known
model name and will produce an API error on every invocation unless overridden
by `WIKI_DIGEST_MODEL`. The default should be a real, current model name.

### C-8 🟡 `_sgt-response-lock.sh` handles two lock formats silently

The lock acquire function handles `lock_path` as both a hardlink (regular
file with `ln`) and a directory. The directory branch appears to handle a
legacy or corrupted state. There is no comment explaining which format is
current. A stale directory lock from a crashed process falls into a path that
calls `rm -f "$lock_path/pid"` then `rmdir "$lock_path"` — if either fails,
the error message says "Could not recover response lock directory" with no
recovery instruction.

**Fix:** Document which format is current and whether the other format is
legacy. If the directory branch is legacy, add a comment with a removal date.

## 5. Performance

### P-1 `sgt-dispatch` and `sgt-context` each run 8–10 `yq` subprocesses per repo

For a 10-repo project, `sgt-dispatch` issues approximately 80 `yq`
subprocess calls during config loading. `yq` is not cheap to start (typically
15–40 ms per invocation on macOS). A 10-repo dispatch touches 800–3200 ms of
`yq` startup time alone before any git or tmux work.

**Recommended fix:** Add a `_sgt_repo_fields_json` lib function that emits all
fields for a named repo in one `yq` call returning JSON, then parse with
`jq` or Python. This reduces per-repo `yq` calls to 1.

```bash
_sgt_repo_fields_json() {
  local config="$1" rname="$2"
  yq -o=json ".repos[] | select(.name == \"$rname\")" "$config"
}
```

### P-2 `sgt-td-list` JSON mode spawns 2N Python processes for N repos

In JSON mode, each repo results in two `python3` invocations: one to tag
tasks with `_repo`, and one to merge-sort the accumulated JSON. For a 10-repo
project this is 20 Python subprocess launches.

**Recommended fix:** Collect all JSON from `td list` into a bash array (one
`td` call per repo), then pass all of it to a single Python process that tags
and merges in one pass.

### P-3 `sgt-cleanup` calls `lsof` twice per cleaned repo

`lsof` on macOS takes 500–2000 ms per invocation. `sgt-cleanup` calls it
once for the validation worktree and once for the main worktree (via
`_worktree_cwd_pids`). For a 5-repo task this is potentially 10 `lsof`
calls, adding 5–20 seconds to cleanup.

**Recommended fix:** Call `lsof` once with all target paths combined if
multiple worktrees are being cleaned. Alternatively, accept the cost
(cleanup is infrequent) but document it.

### P-4 `sgt-graphify` copies entire repos with `tar | tar` before extraction

When exclusions are needed, `sgt-graphify` stages a full copy of each repo:

```bash
tar -C "$path" "${tar_exclude_args[@]}" -cf - . | tar -C "$scan_root" -xf -
```

For a large repo (hundreds of MB), this copies everything except excluded
paths. If `graphify extract` supported exclude flags natively this staging
step would be unnecessary. Until it does, consider using `rsync --exclude`
which is more incremental and can resume partial copies.

### P-5 `oc-inject` polls at 50 ms with up to 300 attempts (15 seconds total)

The delivery confirmation loop:

```bash
while [[ ! -f "$ack" ]]; do
  …
  sleep 0.02
  attempt=$((attempt + 1))
  if [[ "$attempt" -ge "$ack_attempts" ]]; then   # default 300 → 6s
```

This generates 50 filesystem polls per second. On macOS the filesystem event
latency means `inotifywait` is not available, but `sleep 0.1` with 60
attempts (6 seconds) would reduce the polling rate by 5× at no practical
latency cost for interactive use.

## 6. Architecture observations

### A-1 No fleet state schema version

The fleet state directory (`$FLEET_DIR/$TASK_ID/`) has no version file. When
the format changes, migration code is added ad hoc inside individual scripts
(e.g., `_migrate_legacy_response_state` in `sgt-respond`). A `schema_version`
file written at dispatch time would make migration conditions unambiguous and
enable a future `sgt-upgrade` command.

### A-2 The notification/response protocol is spread across five files with no canonical schema

The file names, field names, and proof-chain semantics for the
notification/response protocol are duplicated across:
`_sgt-lib.sh`, `sgt-dispatch`, `sgt-respond`, `sgt-interactive-worker`,
and `sgt-ack-response`.

The protocol state lives in: `.sergeant-notification`,
`.sergeant-notification-acks/<nonce>`, `.sergeant-notification-accepts/<nonce>`,
`.sergeant-notification-complete/<nonce>`, `notification_id`,
`notification_target`, `notification_target_pane_identity`,
`notifications/<id>/targets/<nonce>/{pane_identity,delivered,accepted,completed,acknowledged}`.

There is no single document that describes this protocol and its invariants.
A `docs/notification-protocol.md` would make future changes tractable and
help diagnose stuck notifications.

### A-3 No `sgt-cancel` command

There is no command to cancel an in-progress task cleanly. Users must
manually kill processes and then call `sgt-cleanup --force` (which does not
exist either). `sgt-cleanup` currently refuses non-terminal repos. A
`sgt-cancel <task-id>` that marks repos `failed: cancelled`, stops workers,
and then runs cleanup would complete the lifecycle surface.

### A-4 `sgt-td-create` is an internal command appearing as user-facing

The toolbelt table in `AGENTS.md` lists `sgt-td-create` with the annotation
"called automatically by sgt-dispatch". If it is also user-facing, document
the use cases. If it is internal, prefix it with `_` or remove it from the
toolbelt table.

### A-5 `sgt-watch --list` shows all tasks without project filter

`sgt-watch --list` scans the entire fleet directory. When multiple projects
are active this is noisy. A `sgt-watch --list <project>` filter (matching
task `brief.md` project lines) would make the output useful in multi-project
contexts.

### A-6 `sgt-td-memory` name is obscure

The script records non-secret recovery pointers in the td task log. Its name
suggests it is about td memory management. `sgt-td-checkpoint` or
`sgt-td-handoff` would better convey its purpose. Renaming is low-priority
but the current name causes confusion.

## 8. What is working well

- **Intent pinning** — the three-way SHA check across fleet, repo state, and
  worktree is thorough and has test coverage.
- **Pane identity binding** — using `#{pane_dead}|#{pane_id}|#{pane_pid}|#{pane_created}`
  as the identity string correctly detects PID reuse without a kernel race.
- **Response lock** — the hardlink-based mutex is correct and handles stale
  locks; it just needs documentation on which format is current.
- **Atomic write discipline** — `tmp.$$` + `mv` pattern is used consistently
  for all state-file writes. There are no `echo > file` writes in state-bearing paths.
- **`sgt-graphify` publish safety** — the swap-via-rename and previous-output
  restore on failure is a good pattern for the multi-second graphify run.
- **`_sgt-intent.sh` validation** — the `awk`-based section validator is
  correct, compact, and testable.
- **Test suite coverage** — the tests in `tests/` cover the high-complexity
  scripts (`sgt-dispatch`, `sgt-cleanup`, `sgt-respond`, `sgt-ack-response`,
  `sgt-watch`, `sgt-validate`) which is the right prioritisation.

Findings

verified   The four independently hand-built "sergeant/<run-id>" constructions are genuinely gone, not just renamed

dag.BranchName(runID) is deleted outright (not left as a dead, unused function — grep -rn 'dag\.BranchName' and grep -rn 'func BranchName' both return nothing in internal/dag). The three fmt.Sprintf("sergeant/...") constructions in ui/server.go's handleCreatePR, mcp/server.go's sergeant_seal_pr case, and runner/runner.go's DeliverPullRequest fallback are each replaced with a Store.GetRun lookup followed by naming.BranchName(run.Type, run.ChangeID). A repo-wide grep for the literal substring "sergeant/ turns up only Producer envelope labels ("sergeant/ui", "sergeant/runner", "sergeant/mcp"), a wholly unrelated field that happens to share the same string prefix by coincidence, not a missed branch-name construction.

verified   The import-cycle justification for moving BranchName to internal/naming is real, not a pretext

internal/runner/runner.go's import block is handoff, naming, redact, store — no dag. Separately, internal/dag/engine.go imports runner (for phase execution). Had BranchName stayed in internal/dag and runner.DeliverPullRequest needed to call it, runner would need to import dag, which already imports runner — a genuine cycle Go's compiler would reject. internal/naming has no internal-package imports at all (confirmed by reading its full import list), making it a correct, dependency-free home. I did not rely on go build ./... succeeding as the only evidence here, per the review brief's own caution that this is necessary but not sufficient — I read the actual import lists of both packages.

verified   handleDispatch's work-type validation runs where design.md says it must, with the exact vocabulary

Reading internal/ui/server.go lines 1360–1487 in sequence: JSON decode → brief-emptiness check → validateWorkType(req.Type) → config.LoadProject → runner.ValidateAgent → O3's change resolution (changeRepo/resolveChange) → the no-repos/explicit-repos fork. The type check is the first substantive validation after basic request-shape checks, strictly before anything that resolves a change, validates an agent, or writes a row — matching both design.md's stated placement ("mirrors ValidateAgent's existing placement") and the spec's three scenarios (recognized accepted; missing refused; unrecognized refused, naming the valid set) verbatim. validWorkTypes is exactly {feat, fix, refactor, docs, chore, test} — 6 entries, matching proposal.md's stated set with no additions or omissions.

verified, complete   No hand-copied runs/intents column list was missed

Every query that reads a full RunRecord or IntentRecord row — GetRunByRequestID, ListRecentRuns, GetRun, ListRunsForProject, and ReconcileOrphanedRuns (a different file, internal/store/reconcile.go, easy to miss in a same-file grep) for runs; GetIntent, ListIntentsForProject, ListIntentsByStatus for intents — uses the shared runColumns/scanRun or intentColumns/scanIntent, both newly introduced by this diff. I specifically checked reconcile.go because it is a separate file from store.go and the kind of query design.md's own grep instructions (FROM runs) would still have caught, but a less careful same-file-only search would not. Both INSERT statements (CreateRun, CreateIntent) list type explicitly alongside the other columns. The two remaining narrow queries (SELECT id FROM runs WHERE slug... for slug backfill, SELECT slug, status FROM runs WHERE slug != '') are intentionally column-limited for a different purpose and were never full-row column lists to begin with.

verified, mutation-tested independently   Plan approval genuinely reuses the plan's originally proposed type, not a re-derived one

I did not trust the shipped TestApprovingAPlanReusesItsRecordedType alone. I wrote my own throwaway test proposing a plan with type: "refactor" — deliberately a different type than the shipped test's "chore", so a coincidental default or hard-coded value in the handler could not pass both by accident — approved it through POST /api/plans/{id}/approve, and asserted the resulting run's Type was exactly "refactor" and non-empty. It passed. I then mutated handleApprovePlan's call to createRunAndDispatch, changing the final argument from intent.Type to the literal "", and reran both my test and the shipped one: both failed, reporting run.Type == "" — exactly the predicted symptom of "re-derived instead of reused" degenerating to "not carried forward at all." I restored the file, confirmed git diff --stat internal/ui/server.go was empty, deleted my throwaway test file, and reran go build ./... && go test ./internal/ui/... -count=1 clean. This is the same class of bug as the change-reuse fix reviewed in this codebase's Review 020/021 history (handleApprovePlan previously re-resolved the OpenSpec change instead of reusing the one recorded at proposal time); this diff applies the identical "read the recorded fact back, don't re-derive" fix to the work type, and it is genuinely wired, not merely threaded through a signature that some caller ignores.

verified, real   The dispatched branch is actually named <type>/<change-id> in real git, and PR creation targets the same branch

TestDispatchedBranchIsNamedByItsTypeAndChange and TestCreatePRTargetsTheExactBranchThatWasCreated (both in internal/ui/work_type_test.go) both pass. The first checks git rev-parse --abbrev-ref HEAD inside the real fleet worktree and git show-ref --verify --quiet refs/heads/<branch> against the real source repo — genuine git state, not naming.BranchName compared against its own output. The second stubs Server.GHPRCreate to capture the branch argument gh pr create would have been invoked with, and separately checks the API response's own branch field — both equal the branch git show-ref confirms actually exists. This directly satisfies specs/work-type/spec.md's "Pull-request creation targets the same branch that was actually created" scenario with real, not computed, evidence.

real gap, non-blocking for this diff's own stated scope   A pre-migration run or intent has Type == "", and two of the five naming.BranchName call sites have no guard against it

The shipped TestOpenAddsTypeColumnsToAnOlderDatabase (internal/store/work_type_test.go:85-183) proves, deliberately and by design, that a run or intent row written before this migration reads back with Type == "" — "nothing to backfill" is the comment's own words, and this is the correct, intentional behavior for the migration itself. The gap is downstream of that: describeDelivery (internal/ui/server.go:1701-1702) does if run, err := srv.Store.GetRun(runID); err == nil { branch = naming.BranchName(run.Type, run.ChangeID) } — GetRun succeeds for a legacy row (it has no reason not to), so branch becomes naming.BranchName("", "<change-id>") = "/<change-id>", not the row's real historical branch, which is actually named "sergeant/<run-id>" (the pre-this-change format dag.BranchName used to compute correctly for exactly this case). handleCreatePR (:652-658) has the identical shape: it 500s only if GetRun itself errors, never if Type is empty, and would attempt gh pr create --head "/<change-id>" for a legacy run. I confirmed by direct inspection of naming.BranchName's one-line body (return workType + "/" + changeID) that this is not a hypothetical — it is the literal, unconditional output for an empty workType. No test in this diff exercises describeDelivery or handleCreatePR against a Type == "" row; the shipped tests that reach these two functions all dispatch through the validated path, so they always carry a real type. Severity: this only affects runs and proposed intents already sitting in a database that predates this deploy — proposal.md's own out-of-scope section only disclaims reclassifying old rows, not the narrower, more specific fact that new code reading old rows now computes a wrong-but-plausible-looking value instead of erroring or falling back to the old format. This does not fail any scenario in specs/work-type/spec.md, all of which describe dispatches made through the validated path from now on — but it is a real, silent regression in describeDelivery's branch report for any run that existed before this commit, and it was not evaluated in the builder's own stated verification (which covers "the branch created," not "the branch computed for a pre-existing run").

Verdict

MEETS SPEC WITH CAVEATS. Every scenario in specs/work-type/spec.md is genuinely implemented: a dispatch without a recognized type is refused before any run, intent, or worktree exists; the stated type is durably recorded on the run and, for a proposed plan, the intent; approving a plan reuses the plan's originally recorded type rather than re-deriving or defaulting it (independently mutation-confirmed by me, not just trusted from the shipped test); and the dispatched branch is genuinely named <type>/<change-id> in real git, with gh pr create targeting that exact same branch. The four independently hand-duplicated "sergeant/<run-id>" constructions this change set out to consolidate are genuinely gone — a repo-wide grep confirms zero remaining hand-built branch-name literals, and all five real call sites of naming.BranchName converge on a real Store.GetRun lookup, not a passed-through literal. The import-cycle reasoning for relocating BranchName to internal/naming is real, confirmed by reading runner.go's own import list rather than relying on go build succeeding alone. The runColumns/intentColumns consolidation is complete, including a query in a separate file (reconcile.go) that a same-file-only grep would have missed. The one caveat: a run or intent row written before this migration reads back with Type == "" (proven by the shipped TestOpenAddsTypeColumnsToAnOlderDatabase), and two of the five naming.BranchName call sites — describeDelivery and handleCreatePR — have no guard against this, silently computing a malformed "/<change-id>" branch name for such a row instead of the row's real historical "sergeant/<run-id>" branch, or an explicit error. This does not fail any scenario the spec actually states (all of which describe dispatches made through the validated path going forward), and proposal.md explicitly disclaims reclassifying historical rows — but it does not address the narrower, concrete fact that new code now reads old rows and produces a plausible-looking wrong answer rather than an error, for as long as any pre-migration run or proposed plan exists in a database that has taken this upgrade. This is a real, reportable gap, not a blocking defect against the diff's own stated scope.

Findings

verified   SealBulletForRun is scoped to exactly one bullet, not the run's whole intent

Design.md's stated reason for a new method instead of reusing AdvanceBulletsForRun — that sealing is a per-repo fact, not a run-wide gate outcome — is genuinely implemented, not just asserted in a comment. The function loops ListBulletsForIntent's result and matches on b.Repo == repo, returning as soon as it finds (or refuses) that one bullet; it never calls UpdateBulletStatus on any other bullet in the loop. TestSealBulletForRunAffectsOnlyItsOwnRepoBullet proves this with a real multi-repo intent (api and web bullets), asserting the web bullet is still green after sealing api — not merely that sealing api succeeded.

verified   Refusal names the bullet's actual status, and writes nothing

Both layers get this right and both are asserted specifically, not generically. At the store layer, SealBulletForRun's error text is fmt.Errorf("bullet %q for repo %q is %q, not green — refusing to seal", ...), and TestSealBulletForRunRefusesNonGreenBullets checks strings.Contains(err.Error(), status) for each of pending/red/sealed/failed, then re-reads the bullet via ListBulletsForIntent to confirm its status did not change — a real no-write check, not just "err != nil". At the HTTP layer, TestCreatePRForNonGreenBulletIsRefusedAndNeverInvokesGH checks the same thing against the 409 response body. This is exactly the kind of specific assertion this project's spec explicitly asked for (tasks.md: "assert this the same way this session has asserted 'no subprocess invocation' elsewhere") and it is present, not skipped.

verified   The seal guard runs before gh, through a real dependency-injection seam, confirmed by my own mutation

Server.GHPRCreate is a genuine struct field (func(repoPath, title, body, branch string) ([]byte, error)), defaulted in NewServer to the real subprocess call (runGHPRCreate, a plain function wrapping exec.Command("gh", "pr", "create", ...)), and handleCreatePR calls srv.GHPRCreate(...) rather than shelling out inline. This is a real seam a test can substitute, not a status-code inference. I mutation-tested the ordering myself: wrapped the SealBulletForRun guard block in handleCreatePR with if false { ... }, disabling it entirely, and reran TestCreatePRForNonGreenBulletIsRefusedAndNeverInvokesGH and TestCreatePRForGreenBulletSucceedsAndSealsTheBullet. Both failed exactly as expected: the refusal test got HTTP 200 instead of 409 for all four non-green statuses (the request proceeded to create a local worktree PR), and the seal-on-success test found the bullet still green instead of sealed after a successful create-PR call. I reverted the exact original text and confirmed git diff is empty afterward — this guard is load-bearing, not decorative.

verified   gh pr create is never invoked for a refused request, proven by a real call counter

TestCreatePRForNonGreenBulletIsRefusedAndNeverInvokesGH installs a stub on srv.GHPRCreate that increments a local ghCalls counter and asserts ghCalls != 0 is a failure, for each of the four non-green statuses. This is precisely the "recording wrapper... not just checking the HTTP status" tasks.md called for, and it is genuinely present — not a weaker truthiness check that would still pass if the guard silently no-opped after invoking gh anyway.

verified   A successful seal is verified through the real listing endpoint, not internal state

TestCreatePRForGreenBulletSucceedsAndSealsTheBullet makes a real POST /api/create-pr request, then makes a second real GET /api/bullets?run_id=... request and decodes the JSON response to confirm the bullet reads back as sealed. This exercises the write path and the read path as two independent real HTTP round-trips through the same mux, which is stronger evidence than asserting against the store directly — a bug in handleBullets's intent-resolution logic would also be caught here, not just a bug in the write.

verified   GET /api/bullets matches every scenario in spec.md

bad   AKIA/AIza keys glued to trailing alphanumeric text are not redacted at all

apiKeyPattern's doc comment explains that the leading \b was deliberately dropped so a secret glued to preceding non-whitespace text still matches — and that fix (from b600915) genuinely works; I confirmed it with my own probe inputs like "xsk-abc...NOPx" and {"key":"sk-abc...NOP"}, all correctly redacted. But two of the eight named prefixes, AKIA[A-Z0-9]{16}\b and AIza[A-Za-z0-9_\-]{35}\b, still carry a trailing \b with a fixed repetition count. When a real key is immediately followed by more alphanumeric characters with no delimiter, the regex requires a word-boundary transition that does not exist at that position, and — because the count is fixed rather than open-ended — the engine cannot back off to a shorter match either. The result is a complete miss, not a partial one.

Exact reproduction (run in internal/redact, calling the unexported Text):

Text("AKIAIOSFODNN7EXAMPLEXTRACHARS")
// output: "AKIAIOSFODNN7EXAMPLEXTRACHARS"  (unchanged — the full AWS key leaks verbatim)

Text("AIzaSyD-9tSrke72PouQMnMX-a7eZSW0jkFMBWYEXTRACHARS")
// output: "AIzaSyD-9tSrke72PouQMnMX-a7eZSW0jkFMBWYEXTRACHARS"  (unchanged)

By contrast the other six prefixes (sk-, gh[oprsu]_, xox[bpoa]-) use open-ended {20,}/{10,} quantifiers with no trailing \b, so the same glued-suffix shape redacts correctly for them (over-redacting the trailing junk along with the key, which is safe). This is a narrow but real and reproducible gap in exactly the class of input ("no separator ... glued directly to adjacent non-whitespace text") the design doc's own comment says it set out to close — it only closed the leading side for these two prefixes, not the trailing side.

bad   Agent-authored envelope.json completely bypasses redaction — undisclosed in proposal.md

RunAgentPhase has two ways to build the envelope it persists: synthesize one from outBuf (the branch this bullet correctly redacts), or read one the agent wrote itself at .sergeant/envelope.json (runner.go:447–451, taken whenever the file exists and the phase did not fail). The second branch is _ = json.Unmarshal(data, &env) — nothing between that call and the writes to EnvelopeRecord.Data and PhaseRecord.Payload touches redact.Text or redact.Truncate at all. This is the exact mechanism the plan-file progress-reporting feature (planPromptExtension, wired earlier this session) instructs agents to use, so it is a live, reachable path, not a hypothetical one.

I confirmed the leak directly with a throwaway test: a fake agent script writes .sergeant/envelope.json containing {"payload":{"raw_output":"API_KEY=sk-abc...NOP"}}, then RunAgentPhase is called normally.

env.Payload = {"model":"","provider":"","raw_output":"API_KEY=sk-abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOP"}
// same raw secret also present verbatim in the persisted PhaseRecord.Payload
// and in the persisted EnvelopeRecord.Data — neither field passes through redact.Text

proposal.md's problem statement is built entirely around an agent taking a plausible, legitimate-looking action (running env, git remote -v, or cat-ing a .env file) and that content ending up unredacted in a durable record. An agent that reports that same content through its own envelope.json instead of stdout hits exactly this gap, and the gap is not named anywhere in proposal.md's "Out of scope" section — which lists subprocess env inheritance, the metadata/content schema split, retention policy, and retroactive redaction as the accepted gaps, but says nothing about this second envelope-construction path. tasks.md's own instruction is scoped narrowly enough to explain why: it names only "the raw_output: stripANSI(outBuf.String()) map entry" in RunAgentPhase, i.e. the synthesized branch specifically, so the code is not in violation of the literal task text — but the requirement text (R4.4: "must not retain credentials, tokens, ... in logs, records, responses") and the spec's stated intent are not met on this path, and no test in this diff (including the new TestAgentAuthoredEnvelopeStillGetsProvenance, which uses only {"custom":"value"} as its payload) would ever catch a secret placed here.

Verdict

MEETS SPEC WITH CAVEATS. Every scenario literally named in specs/output-redaction/spec.md is implemented and correctly tested: the three named pattern classes redact while leaving surrounding text and NAME/header-name intact, truncation is bounded with a visible marker, and redaction demonstrably runs before truncation at both real call sites — I confirmed the ordering myself with a mutation test on RunCodeGate, not just by reading the source. The pre-merge fix to RunCodeGate.Command (which the commit message credits to the dispatched agent's own tests) is real and is itself exercised by a test that embeds the secret in the command string, not only in its output. Scope discipline is complete: no config field for the size limit or patterns, no changes to internal/dag/engine.go or any cmd.Env line, no retention/deletion logic, no modification of historical rows.

Two caveats keep this from a clean "genuinely met," both with concrete reproductions above and neither caught by any test in this diff. First: AKIA and AIza, two of the eight named provider-key shapes, use a fixed-length pattern with a trailing \b that silently fails to match when the real key is glued directly to more alphanumeric text with no delimiter — the full raw key then leaks verbatim. This is the same class of boundary bug the pre-merge fix (b600915) explicitly set out to close, but that fix only addressed the leading side for these two prefixes; the trailing side was missed. Second, and more significant: RunAgentPhase's agent-authored-envelope.json branch — a live, reachable path already used by this session's own plan-file progress-reporting mechanism — never calls redact.Text or redact.Truncate at all, so a secret an agent includes in its own envelope payload is persisted to both PhaseRecord.Payload and EnvelopeRecord.Data completely unredacted. This is not a violation of tasks.md's literal text, which names only the synthesized-envelope raw_output map entry — but it is squarely within R4.4's actual requirement text and proposal.md's own stated threat model (an agent's plausible, legitimate- looking action putting secret content into a durable record), and proposal.md's "Out of scope" section does not mention this second envelope-construction path at all. It is an undisclosed gap, not an accepted one.

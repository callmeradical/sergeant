dag.BranchName(runID) is deleted outright (not left as a dead, unused function — grep -rn 'dag\.BranchName' and grep -rn 'func BranchName' both return nothing in internal/dag). The three fmt.Sprintf("sergeant/...") constructions in ui/server.go's handleCreatePR, mcp/server.go's sergeant_seal_pr case, and runner/runner.go's DeliverPullRequest fallback are each replaced with a Store.GetRun lookup followed by naming.BranchName(run.Type, run.ChangeID). verified   The import-cycle justification for moving BranchName to internal/naming is real, not a pretext

internal/runner/runner.go's import block is handoff, naming, redact, store — no dag. Separately, internal/dag/engine.go imports runner (for phase execution). Had BranchName stayed in internal/dag and runner.DeliverPullRequest needed to call it, runner would need to import dag, which already imports runner — a genuine cycle Go's compiler would reject. internal/naming has no internal-package imports at all (confirmed by reading its full import list), making it a correct, dependency-free home. I did not rely on go build ./... succeeding as the only evidence here, per the review brief's own caution that this is necessary but not sufficient — I read the actual import lists of both packages.

real gap, non-blocking for this diff's own stated scope   A pre-migration run or intent has Type == "", and two of the five naming.BranchName call sites have no guard against it

The shipped TestOpenAddsTypeColumnsToAnOlderDatabase (internal/store/work_type_test.go:85-183) proves, deliberately and by design, that a run or intent row written before this migration reads back with Type == "" — "nothing to backfill" is the comment's own words, and this is the correct, intentional behavior for the migration itself. The gap is downstream of that: describeDelivery (internal/ui/server.go:1701-1702) does if run, err := srv.Store.GetRun(runID); err == nil { branch = naming.BranchName(run.Type, run.ChangeID) } — GetRun succeeds for a legacy row (it has no reason not to), so branch becomes naming.BranchName("", "<change-id>") = "/<change-id>", not the row's real historical branch, which is actually named "sergeant/<run-id>" (the pre-this-change format dag.BranchName used to compute correctly for exactly this case). handleCreatePR (:652-658) has the identical shape: it 500s only if GetRun itself errors, never if Type is empty, and would attempt gh pr create --head "/<change-id>" for a legacy run. I confirmed by direct inspection of naming.BranchName's one-line body (return workType + "/" + changeID) that this is not a hypothetical — it is the literal, unconditional output for an empty workType. No test in this diff exercises describeDelivery or handleCreatePR against a Type == "" row; the shipped tests that reach these two functions all dispatch through the validated path, so they always carry a real type. Severity: this only affects runs and proposed intents already sitting in a database that predates this deploy — proposal.md's own out-of-scope section only disclaims reclassifying old rows, not the narrower, more specific fact that new code reading old rows now computes a wrong-but-plausible-looking value instead of erroring or falling back to the old format. This does not fail any scenario in specs/work-type/spec.md, all of which describe dispatches made through the validated path from now on — but it is a real, silent regression in describeDelivery's branch report for any run that existed before this commit, and it was not evaluated in the builder's own stated verification (which covers "the branch created," not "the branch computed for a pre-existing run").

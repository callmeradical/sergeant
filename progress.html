Verdict: R5.5 is genuinely met, not just apparently met. This is the first of the last three R5-bullet reviews where the "green tests, quietly incomplete requirement" pattern (Review 007's next_attempt_at/error-classification gap, the earlier CausationID incident) did not recur. I could not make it recur either: two required mutation tests behaved exactly as the commit message claims (with slightly more test breakage than claimed, not less), and three additional probes I wrote myself — a second dead-letter episode after a failed replay, a replay that itself needs an internal retry before succeeding, and a literal removal of the quarantine-refuses-replay guard — all produced correct behavior or a correctly-failing test. The only real findings are a test-rigor gap (real behavior is correct but under-tested for multi-episode/multi-attempt paths) and one over-cautious assertion that is weaker than it looks. Neither blocks the R5.5 verdict.

TestDeadLetterCriticalFailsCaller (s-4) and TestDeadLetterNonCriticalDoesNotFailCallerButIsRecorded (s-5) both genuinely exercise the flag: s-4 asserts a non-nil error, s-5 asserts a nil error and that the dead-letter row still exists — this is the distinction the spec draws explicitly ("a silently dropped notification and a non-critical dead letter must not look the same from the store's point of view"), and the test checks both halves, not just the return value. The honest-partial framing in proposal.md ("mechanism real and tested, not yet exercised by any caller") is accurate; there is no hidden third call site that secretly passes false.

verified   The quarantine-refuses-replay guard is a real guard, confirmed by actually disabling it

My first attempt at this mutation (removing the case deliveryStateQuarantined arm from ReplayDelivery's switch) did not break any test, because the switch's default arm also refuses (any state that isn't dead_letter/delivered/ acknowledged/"" falls through to the same "not dead_letter" refusal). That is not a bug — refusal is still correctly enforced either way — but it means that specific code path is not uniquely exercised by that mutation. I then made the guard actually permit a quarantined delivery to replay (added deliveryStateQuarantined to the "permitted" case), which is a faithful reproduction of "disable the guard":

mutation: `case deliveryStateDeadLetter, deliveryStateQuarantined: // permitted`
  -> FAIL TestDeadLetterQuarantinedDeliveryRefusesReplay (s-11)
     "expected error when replaying a quarantined delivery, got nil"
     "row count changed after refused replay: before=5 after=7"
tree restored with git checkout --

So the guard is real and load-bearing, matching the commit message's claim, via the row-count and call-count assertions in the same test. The mechanism works; see the next item for the one assertion in that same test that is weaker than it looks.

low   One assertion in s-11's test is weaker than it appears, though the test as a whole is not

TestDeadLetterQuarantinedDeliveryRefusesReplay asserts strings.Contains(err.Error(), "quarantine") to check that the refusal "names the quarantine," per the spec text. But the generic fallback error ("...latest state is %q, not dead_letter", with latest="quarantined") also contains the substring "quarantine" purely because Go's %q verb quotes the state name itself — so this one assertion would pass even if the explicit case deliveryStateQuarantined branch (with its more specific message, "delivery is quarantined") were deleted and the state fell through to default. It is not, on its own, proof that the code recognizes quarantine as a distinct case rather than an incidental string match. This does not change the verdict: the same test's row-count and call-count assertions (see previous item) do catch a genuine guard removal, so the guarantee the scenario cares about — a quarantined delivery cannot be replayed — is actually verified, just not by the substring check specifically.

medium   Multi-episode dead-letter cycles and multi-attempt replays are correct but have zero coverage in the merged suite

The review brief specifically asked about this because it is exactly the kind of edge the shared deliverRetryLoop refactor could get wrong: a delivery that is dead-lettered, replayed, fails again (a second dead-letter episode), and is then quarantined or replayed again; and a replay that itself needs more than one internal attempt before resolving. Neither path is exercised by any test in delivery_test.go — every replay test either succeeds on the replay's first attempt (TestDeadLetterCanBeReplayed, TestDeadLetterAlreadyResolvedIsNotReplayedTwice) or is refused before an attempt is made. I wrote both cases myself:

Second dead-letter episode (dead_letter -> replay fails 3x -> dead_letter -> quarantine -> replay refused):
  history: pending(1) retrying(2) retrying(3) dead_letter(3)
           pending(4) retrying(5) retrying(6) dead_letter(6)
  quarantine succeeds (latest state correctly read as the SECOND dead_letter row, attempt=6)
  further replay correctly refused
  -> PASS (mechanism correct)

Replay needing an internal retry (dead_letter after 3 attempts -> replay fails once, succeeds on 2nd try):
  history: pending(1) retrying(2) retrying(3) dead_letter(3)
           pending(4) retrying(5) delivered(5)
  attempt numbering continues correctly from 4, not restarting at 1
  -> PASS (mechanism correct)

Both throwaway tests written, run, and deleted; tree confirmed clean after (git status --short).

latestDeliveryState's ORDER BY created_at DESC, id DESC correctly picked the second (later) dead_letter row in the first case, not the first one — the mechanism is correct today. But nothing in the shipped suite protects this correctness going forward: a future change to deliverRetryLoop's attempt-numbering, or to latestDeliveryState's ordering, that broke either path would pass the entire merged test file. This is a real coverage gap against the review brief's own stated risk ("check it actually produces correct attempt numbering and history for a replay that itself needs multiple internal attempts, not just a replay that succeeds on the first try") — the code passed my probe, but the shipped tests did not ask the question.

verified   Migration path is correct for both fresh and upgraded databases

The createDeliveriesTable DDL constant itself was not updated to include recovery_instructions — only migrateAddColumns gained a new {"deliveries", "recovery_instructions", "ALTER TABLE ..."} entry, following the same pattern already used for error_class. This looked at first read like it might leave a freshly-created database without the column, but Open() unconditionally runs migrateAddColumns() immediately after CREATE TABLE IF NOT EXISTS on every open, including the very first one — so a brand-new database and an upgraded one converge on an identical schema. go test ./internal/store/..., which opens a fresh temp-file database per test, passing with RecoveryInstructions populated confirms this in practice, not just by reading the code.

low   insertDeliveryRowWithInstr is a pointless pass-through wrapper, harmless but worth naming

The task description anticipated this exact function might "hide" something. It doesn't — it is a byte-for-byte forward of every argument to insertDeliveryRow, which itself already gained the recoveryInstr parameter in this same diff. The wrapper's own doc comment ("...accepts an explicit recovery_instructions string...") describes something insertDeliveryRow already does directly. This is dead indirection left over from what was probably an earlier draft of the refactor, not a functional issue — confirmed harmless by direct comparison of the two function bodies. Low severity: worth deleting for clarity, not worth blocking on.

low   Inherited, not new: ReplayDelivery/QuarantineDelivery's state-guard check is a non-atomic read-then-insert, same class of gap Review 007 flagged for DeliverEnvelope

Both new functions read latestDeliveryState, decide, then insert — with no transaction wrapping the two — so two concurrent callers could both observe dead_letter and one insert a quarantined row while the other's replay attempt is already in flight, producing a history where "latest state" briefly disagrees with what an operator intended. This is not exploitable today: ReplayDelivery and QuarantineDelivery have zero callers anywhere in the codebase (bullet 4/R5.6 has not landed), so there is no concurrent caller to race. This is the same tradeoff Review 007 named for DeliverEnvelope's idempotency check, extended to two more functions built on the same pattern, and it is equally undisclosed in proposal.md as a known limitation. Worth naming now, as Review 007 did, rather than rediscovering it once bullet 4 adds a caller.

Verdict

R5.5: genuinely met. Exhausted retries durably produce a dead_letter row (not failed) carrying the envelope reference, classified error, and a non-empty recovery-instructions string; the critical flag correctly gates whether a dead letter fails its caller, and both real production call sites preserve prior behavior by passing a literal true; ReplayDelivery and QuarantineDelivery are real, correctly state-guarded, auditable actions over the same insert-only history, and both mechanisms hold up under edge cases the merged suite itself does not test (a second dead-letter episode, a replay needing multiple internal attempts) — I verified this myself rather than trusting the absence of a failing test. All 11 spec scenarios have a test that genuinely matches its Given/When/Then, not just its name. No scope creep into bullet 4's CLI/UI/MCP surfaces, no UnquarantineDelivery, no automatic replay sweep.

Severity-ranked residual findings, none of which change the verdict: (1) medium — multi-episode dead-letter cycles and multi-attempt replays are correct but have zero test coverage in the merged suite, so a future regression in deliverRetryLoop's attempt-numbering or latestDeliveryState's ordering would not be caught; (2) low — one assertion inside s-11's test (a substring check for "quarantine" in the error message) is weaker than it looks and would not by itself catch the removal of the specific quarantine-detection branch, though the same test's other assertions do; (3) low — insertDeliveryRowWithInstr is dead pass-through indirection, harmless; (4) low, inherited from bullet 2 — the state-guard read-then-insert in ReplayDelivery/QuarantineDelivery is not atomic, a latent gap once bullet 4 gives these functions a concurrent caller, not exploitable today.

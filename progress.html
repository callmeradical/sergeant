real bug, introduced by this change, not covered by any spec.md scenario   A proposed plan's change is not persisted, so approval can silently resolve — or scaffold — a different one

store.IntentRecord has exactly six fields: ID, Project, Statement, Status, CreatedAt, UpdatedAt. There is no ChangeID. At proposal time, handleDispatch resolves the change via changeRepo(proj, req.Repos) / resolveChange(changeRepoPath, req.ChangeID, req.Brief) before the no-repos gate — but the result is only used to possibly scaffold a directory on disk; it is never written onto the IntentRecord it creates. At approval time, handleApprovePlan re-resolves from scratch with different inputs: changeRepo(proj, targetRepos) (a non-empty list, built from the bullets) and resolveChange(changeRepoPath, "", intent.Statement) — note the hardcoded empty string, discarding whatever change_id the original request named.

Reproduction 1 — explicit change_id discarded. Proposed a plan with change_id="my-explicit-change" (directory pre-created) and brief "totally unrelated free-text intent" (a brief that derives a different slug). Approving it returned "change_created":true, "change_id":"totally-unrelated-free-text-intent" — a brand-new OpenSpec change was scaffolded on disk under a re-derived id, and the dispatched run's ChangeID was that re-derived id, not my-explicit-change. The human who named an explicit change when proposing the plan gets a different, auto-scaffolded one governing the actual dispatched work.

Reproduction 2 — DAG-configured project picks a different repo at approval than at proposal. changeRepo's non-empty-requested branch just picks the first configured repo in the given list, in list order; its empty-requested (proposal-time, no-repos) branch instead prefers proj.DAG.Stages[0].Repos order when a DAG is configured. With two repos — api (alphabetically first) and web (first in the DAG's first stage) — and the change directory existing only under web (where proposal-time resolution puts it), approving the plan resolved the change under api instead, found no existing directory there, and again scaffolded a new, empty change with the same change id under a different repository ("change_repo":"api","change_created":true). The project now has two add-stripe-webhooks change directories in two different repos — one real (under web, unreferenced by the dispatched run), one empty (under api, the one actually recorded).

Neither reproduction requires an unusual setup: an explicit change_id whose slug doesn't match the brief, and a project with a dag: block (a real, documented config field used for cross-repo workflow ordering — not a test-only construct) are both ordinary. Both bugs stem from the same root cause: this feature introduces a real time gap between "the change is resolved" (proposal) and "the run that change governs is created" (approval) that did not exist before this feature — previously, resolution and dispatch happened in one request, so there was nothing to drift. No scenario in specs/plan-approval/spec.md tests change-identity continuity across that gap, which is presumably why this shipped without either the shipped test suite or the "found and fixed before merge" pass catching it. This is a defect in this change's own new code, not an inherited pre-existing gap (contrast Review 019's redaction finding).

minor, cosmetic   A test comment describes the pre-fix behavior

TestApprovingAProposedPlanStartsTheRealDispatchSequence (plan_approval_test.go:210) says the intent and bullets transition out of proposed "even though the dispatch sequence mints a fresh run and a fresh intent of its own (the same thing an explicit-repos dispatch does)." git log -S confirms this line was written in f9faa53, before the intent-reuse fix landed in f84becb, and was never updated. It is now factually wrong — approval does not mint a second intent, which is the entire point of the fix — but no assertion in that test depends on the false claim, so it costs nothing functionally. Worth a one-line correction for a future reader who takes the comment at face value.

Verdict

MEETS SPEC WITH CAVEATS. Every scenario in specs/plan-approval/spec.md is genuinely implemented and genuinely tested: a no-repos dispatch creates a proposed plan and starts nothing (verified against a real empty-fleet-directory seam, not just the HTTP response); an explicit-repos dispatch is provably unaffected; proposed plans are listable with their bullets; approving starts the real dispatch sequence; rejecting starts nothing and leaves the intent abandoned; both actions are idempotent on repeat and refused outside their valid starting state. The specific defect this review was tasked with independently re-verifying — createRunAndDispatch minting a second, disconnected intent on approval — is genuinely fixed: I did not just read the regression test, I reverted the fix myself, watched the test fail with the exact predicted symptom, and restored the code to a byte-identical git diff. The manually-resolved merge conflict in store.go's BulletStatuses() is complete and correct, combining both sibling changes with no loss. Bullet merge order survives approval intact; I traced the exact mechanism rather than trusting the absence of a failing test.

The caveat is a bug I found doing my own independent reproduction that is not exercised by any shipped test or any scenario in the binding spec: a proposed plan does not remember which OpenSpec change it was resolved against (IntentRecord has no ChangeID field), so handleApprovePlan re-resolves the change from scratch at approval time, with different inputs than proposal time used (changeRepo(proj, targetRepos) instead of changeRepo(proj, req.Repos=[]), and a hardcoded empty change_id instead of whatever the caller originally named). I reproduced two concrete failure modes: an explicitly-named change_id that doesn't match the brief's derived slug is silently discarded and replaced with a freshly-scaffolded, differently-named change; and on a project with a dag: block (an ordinary, documented config feature, not a test artifact) whose stage repo order differs from alphabetical order, approval can resolve the change under a completely different repository than proposal did, scaffolding a second, empty change directory with the same id in the wrong repo while the real, populated one sits unreferenced. Both are silent — no error, 200 OK, a dispatched run — and both directly undermine O3's purpose (a durable, singular planning record governs the work), even though O3's literal ordering rule ("the change is resolved before any run or worktree exists") is technically satisfied at both points in time. This is new behavior this change introduces — the propose/approve time gap it creates is exactly what makes drift possible; before this feature, resolution and dispatch happened in the same request and could not drift apart. I recommend persisting the resolved change's identity (id and repo) on the IntentRecord at proposal time and having handleApprovePlan reuse it verbatim rather than re-resolving.

Separately, a one-line test comment in plan_approval_test.go still describes the pre-fix behavior (claims approval "mints ... a fresh intent of its own"); harmless since no assertion relies on it, but worth correcting so a future reader isn't misled.

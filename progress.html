Findings

high   A coordinator crash creates permanently stuck runs (R6.3)

Hit for real this round. The UI server was a child of a shell; an aborted command killed it, and the in-flight run stayed running in the database with nothing executing it.

run rust-newt-taipei      status: running     process: none
POST /api/run-resume  -> refused: "is running and cannot be resumed"

Resume correctly refuses, because it cannot distinguish a live run from an orphan. So the work was unrecoverable through any supported path — not running, and not resumable. R6.3 requires a restarted coordinator to "inspect the durable run and phase records and report the known state"; nothing reconciles on startup.

Worked around, not fixed. Cancelling first made it resumable, and the run then completed. Sergeant was honest throughout — cancel reported "No in-flight run found on this server; status recorded as cancelled only." The fix is startup reconciliation: on boot, a run marked running that this process is not driving must be moved to a terminal, resumable status. Not yet specified.

shipped   Runs now report progress against their plan

An agent phase used to report running and nothing else for most of a run. Sergeant now seeds .sergeant/plan.json from the resolved change's scenarios before the agent starts, the agent marks items as it works, and the existing change stream carries it.

  ◐ ○ ○ ○ ○   0/5   0m00s  build
  ● ○ ● ○ ○   2/5  13m01s  running
  ● ● ● ● ●   5/5  13m08s  passed

Solid circle done, open circle not started, spinner in progress, count beneath. No time estimate is offered, and that is deliberate: across five completed changes, plan size correlates negatively with agent time (r = -0.91) — nine scenarios took 394s while four took 1309s. A percentage bar would have been fabricated.

Reported progress cannot change a status. TestFullyReportedPlanDoesNotPassFailedRun holds the line: a fully reported plan beside a failed gate renders as a failed run. Sergeant seeds the file and thereafter only reads it, and resume deliberately does not re-seed, which would overwrite what the agent had reported.

closed   R2.4 — retry policy is explicit and observable

Delivered by goose, the first requirement it has ever completed. retries resolves repository-first then project default then zero, so an omitted field behaves exactly as before. Gates are excluded deliberately: re-running a failed gate until it passes would turn evidence into a lottery. Confirmed to discriminate — forcing the resolver back to a literal zero fails TestEnginePassesResolvedRetriesToAgentPhase and TestEngineUsesRepoRetryOverride.

high   goose has never worked in v2 — every dispatch to it died before the model saw anything

Found while switching the factory from opencode to goose. BuildAgentCommand produced goose run <prompt>. goose run has no positional text argument.

$ goose run "Create a file named proof.txt containing the word ok"
error: unexpected argument 'Create a file named proof.txt...' found
  -> no file created, the prompt never reached the model

ValidateAgent accepts goose, so sergeant would dispatch happily and report an ordinary agent failure. Nothing distinguished a malformed command from a model that failed. Had the 12 remaining requirements been dispatched to goose first, all of them would have failed this way.

Closed in f148859. Now goose run --no-session --output-format json -t <prompt>. Omitting -s/--interactive matters as much as the -t: goose stays interactive after processing input, so a headless phase would have waited on a terminal that is not there (R2.3). Verified end to end — first successful goose run under sergeant:

agent build  passed  4s     commit 435b7e1, README edited as asked
code  build  passed  1s
code  test   passed  5s
code  vet    passed  0s

designed   Cost capture — goose already records it, keyed by a column sergeant controls

Costs were not captured anywhere. They do not need to be invented: goose writes per-session usage and cost to ~/.local/share/goose/sessions/sessions.db, and the sessions table carries working_dir. Sergeant gives every run its own worktree, so working_dir is a join key onto a run.

sessions: working_dir, total_tokens, input_tokens, output_tokens,
          accumulated_cost, cache_read_tokens, cache_write_tokens,
          provider_name, model_config_json

the goose smoke run above, queried by its worktree:
  tok 15283  in 15263  out 20  cost $0.093  anthropic

This reuses the existing accounting rather than building a second one. tokenmeter already prices spend across tools and tags it by directory pattern; a rule for the fleet root now attributes dispatched work to the project instead of leaving it untagged. Sergeant's own job is to record the measured tokens against the phase — cost is derived from a price table, and inventing one would breach the rule against recording values not derived from stored state.

Not yet implemented in sergeant. The design is verified against real data; the store does not yet hold a usage record per phase. This is a new requirement, not one of the 39.

closed   Nothing advances an intent or a bullet, so the primary table is wrong by design

Dispatch now creates intents and bullets (D4). Nothing ever updates them. UpdateIntentStatus and UpdateBulletStatus have no production callers — only their own definitions and tests.

intents:  in_progress 4   satisfied 2     <- the 2 were set by hand, in SQL
bullets:  pending     4   merged    4     <- the 4 merged were set by hand, in SQL

Worse than the pre-D4 empty table: an empty table was honestly empty, whereas permanently in_progress rows assert something untrue.

Closed. setTerminal now advances the run's bullets, so a dispatch and a resume share one path. Intent status is derived from its bullets rather than assigned by a run, which makes D6 structural: satisfied needs every bullet at merged, and merged is only reachable from observed PR state. Verified on the live server, not only in unit tests — including the two cases most likely to be wrong:

dispatch then cancel -> run=cancelled  bullet=pending  intent=in_progress
dispatch that passes -> run=passed     bullet=green    intent=in_progress
                                                       ^ D6 holds: work done, not delivered

Existing rows were deliberately not backfilled; the defect was the missing transition, and hand-patching again would hide whether the fix works.

The remaining work, largest first

R5 — notification/envelope transport. 7 of 7 unmet, and the single largest block.

The PRD asks for typed, versioned, schema-validated, immutable envelopes with envelope_id, schema_version, producer, correlation_id, causation_id and a full reference chain; a delivery state machine over pending / leased / delivered / acknowledged / retrying / failed / dead_letter; bounded retry with backoff and an idempotency key; dead-letter records with auditable replay and quarantine; and CLI, UI and MCP surfaces over that same transport.

required metadata:  ~15 fields + delivery state machine
EnvelopeRecord has:  ID RunID Repo Stage Summary Artifacts Data CreatedAt
                     (8 fields, no delivery state at all)
grep dead_letter|leased|acknowledged in store: 0 hits

This is the v1 messaging family — sgt-msg-send/recv/ack/list, sgt-respond, sgt-ack-response, sgt-callback, sgt-notify, sgt-wake — restated as a durable Go transport. Estimated 4–6 bullets. Nothing here is started.

D9 — graphify as a native capability. Not started, and it gates the v1 retirement.

grep graphify in internal/**.go: 0 hits
config.Project has no Graphify field (block is parsed and discarded)

This is the load-bearing one for A1. Until graphify exists natively, the v1 proxy stays, and with it 9 extra Go modules, 6 spurious install prerequisites, and a D7-violating shell-out path. Estimated 2–3 bullets.

R4.4 / R4.5 — redaction and content minimisation. Not started.

grep redact|scrub|secret in internal/**.go: 0 hits

The PRD says redaction and retention "must be defined before production release", so this is a release gate rather than a nice-to-have. Related evidence from Review 002: the SSE snapshot ships every run's full brief, 31 KB, which is exactly the operational-metadata-versus-content distinction R4.5 asks for. Estimated 1–2 bullets.

R3.5 — human approval for authorising gates. Not started.

grep approval|awaiting_approval in internal/**.go: 0 hits

D5 names three legitimate interruptions: a plan awaiting approval, a blocked bullet, and a bullet ready for an irreversible step. Only "blocked" is observable today, and only because a run fails. Estimated 2 bullets.

R2.4 — retry policy explicit and observable. Effectively unmet.

internal/dag/engine.go:310  pr.RunAgentPhase(ctx, phase, prompt, 0)
                                                            ^ hardcoded
no retry field in the project config schema

The parameter exists and is always zero. Estimated 1 bullet.

PRD conflicts — the document no longer matches the decisions

R2.4 says every agent phase is "bounded by a strict timeout". It is not, deliberately.

docs/prd-sergeant-v2.md:346  "bounded by a strict timeout"
internal/runner/runner.go:72  DefaultAgentTimeout = 0

The default was removed on purpose, after a 10-minute default killed a run that had already committed passing work. The decision is right and the PRD is stale. A binding document that contradicts the code trains people to ignore it.

R7.3 says the embedded UI can "refine supported project configuration". That was removed.

The dashboard is observation-only now; project YAML is edited in an editor. The /api/refine-project endpoint still exists, so the capability is not gone, but the requirement as written is false.

v1 capabilities that are genuinely out of scope

Not every one of the 33 scripts is a gap. sgt-td-*, sgt-treehouse-init and sgt-no-mistakes-finding integrate separate external tools. sgt-interactive-worker is a tmux concept that D1's agent-driven path replaces rather than reimplements — and tmux is excluded as a factory dependency. sgt-drain / sgt-undrain pause a queue v2 does not have, since measured concurrency has never exceeded one.

Total estimate: 10–14 bullets, of which R5 is roughly half. Plus one document reconciliation pass and one owner decision (A1).

Stated as bullets rather than time, because bullet size is the unit this factory actually delivers in. Recent bullets have run 25s to 22min of agent time each, plus review. The estimate covers reaching the PRD as written, not parity with v1.

Blockers

One decision outstanding: A1 / td-ccc18b. No longer blocking delivery — the native tools are reachable as of 10a9160 without touching the hold. It now blocks three cleanups that all reduce to the same question: does v1 stay?

Cost of holding, measured: 9 extra modules in the Go graph, 6 spurious required install prerequisites including tmux, and a shell-out path D7 forbids. Benefit of holding: 34 working tools that have no native replacement until graphify lands. I am not making this call.

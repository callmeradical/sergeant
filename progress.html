Findings

verified   The "single call site covers both paths" claim is real, confirmed by my own mutation, not the builder's

annotatePayloadWithProvenance is called exactly once, at runner.go:465, after the if data, err := os.ReadFile(envelopePath); err == nil && !failed {...} else {...} block that builds env for either the agent-authored or sergeant-synthesized path, and before every consumer of env.Payload (Router.SaveEnvelope via DeliverEnvelope, Store.RecordEnvelope, Store.RecordPhase). I moved the call inside only the else branch and reran the three provenance tests: TestAgentAuthoredEnvelopeStillGetsProvenance failed exactly as predicted (""/"" instead of claude-sonnet-4-6/anthropic), while TestGooseAgentPhaseRecordsModelAndProvider and TestUnparsedAgentProvenanceIsEmptyNotGuessed both still passed — proof the suite discriminates precisely on this fault rather than failing for unrelated reasons. Reverted with git checkout -- internal/runner/runner.go; confirmed a clean tree and a successful rebuild afterward. This is the exact bug shape the review brief warned had recurred elsewhere in this project, and here it is genuinely absent.

verified   TestAgentAuthoredEnvelopeStillGetsProvenance genuinely exercises the agent-authored path

The test's fake agent is a real shell script (not the shared fakeAgent echo helper used by the other tests) that prints the goose banner, then mkdir -p .sergeant && cat > .sergeant/envelope.json with its own distinct summary ("agent authored this envelope") and a {"custom":"value"} payload key, then exits 0. The test asserts env.Summary == "agent authored this envelope" and payloadMap["custom"] == "value" before checking model/provider — both assertions would fail if the code had silently fallen through to the synthesized-summary template ("Phase build completed for svc"), so the test cannot be satisfied by accidentally re-testing the synthesized path under a different name.

verified   The regex's separator character matches real production goose output, not just the fixtures

The goose-agent envelopes already present in the live sergeant.db (from actual dispatches on this project, unrelated to this change) contain raw_output text reading new session · anthropic claude-sonnet-4-6. Extracting the separator byte and checking it with Python's unicodedata.name() confirms it is U+00B7 MIDDLE DOT — exactly the character gooseBanner's regexp and both test fixtures use (source comments and fixtures could have silently used a visually similar U+2022 BULLET or U+30FB without anyone noticing by eye; I did not rely on eyeballing). Running the exact regex against the real extracted string via Python correctly captured ("anthropic", "claude-sonnet-4-6"). No ANSI escape bytes surround the banner in the real capture either, corroborating design.md's claim that ANSI-stripping is not required before matching.

verified   Empty model/provider are set as explicit keys, not omitted

annotatePayloadWithProvenance runs m["model"] = model; m["provider"] = provider unconditionally — there is no early return or conditional guard for the empty-string case. TestAnnotatePayloadWithProvenanceSetsEmptyKeysExplicitly asserts both keys are present (hasModel/hasProvider via comma-ok map access) and equal to "", which is the correct test for "known absent" vs. "key never set." A JSON null payload is also handled: json.Unmarshal of null into a map produces a nil map with no error, and the code allocates a fresh map before assigning into it, avoiding the nil-map-write panic; TestAnnotatePayloadWithProvenanceHandlesJSONNull covers this directly.

low   Un-anchored regex could in principle match agent-generated text, not just goose's own banner

gooseBanner is applied to the entire captured outBuf.String(), which for a successful phase includes everything the agent printed, not just its startup banner. If the agent's own generated output (e.g. a commit message, a code comment, or a quoted example) happened to contain the literal substring new session · word word, FindStringSubmatch would return that occurrence instead of (or ahead of) the real banner. In practice this is a non-issue today: goose always emits its banner as the very first output before any agent-generated content, so the real banner is always the leftmost match. This is a latent, low-severity risk worth naming rather than a real defect — it does not currently misfire and the spec does not ask for anchoring, but design.md does not discuss it as a rejected alternative the way its other design choices are discussed.

Verdict

R4.6: genuinely met. detectModelProvider correctly parses goose's real startup banner for provider and model (verified against real production-captured bytes, not only test fixtures), returns empty strings for every other supported agent and for unparseable goose output, and never panics across malformed/edge-case inputs. annotatePayloadWithProvenance attaches model/provider to any JSON-object payload, leaves non-object payloads (including JSON null, after nil-map allocation) unchanged or safely defaulted, and sets both keys explicitly even when empty — the honest "known absent" signal the design called for. The single call site in RunAgentPhase is placed after both env-building branches converge and before every downstream consumer of env.Payload; I mutation-tested this myself, independent of the commit message's own claimed mutation test, and the guarantee held. All 4 spec scenarios in specs/phase-provenance/spec.md have a test that genuinely matches its Given/When/Then. No scope creep beyond the proposal's stated boundaries: no parsing added for other agents, no token/cost fields, no CLI/UI/MCP surface, and pr.Model/GOOSE_MODEL request-side behavior is untouched (the diff is insert-only).

One residual finding, which does not change the verdict: low severity — the banner regex is applied un-anchored against the agent's full captured output, so it could in principle match agent-generated text elsewhere in the buffer rather than goose's own banner. Not exploitable today because goose always emits its banner first and FindStringSubmatch returns the leftmost match, but the tradeoff is not discussed in design.md the way its other design choices are.

Findings

verified   The scoping correction is true, not asserted

This bullet's entire "native" framing rests on the claim that v1's sgt-graphify is itself a thin bash wrapper around a separate, already-installed graphify binary. I did not take this on faith: I ran graphify --help myself and got a real, substantial CLI with extract, merge-graphs, query, explain, and affected among its subcommands, and I read v1's 562-line script directly. It calls graphify extract "$scan_root" --out "$repo_root" (line 369) and graphify merge-graphs "${GRAPH_PATHS[@]}" --out "$stage_output/graph.json" (line 437) as external commands, and does no extraction or graph-algorithm work of its own — only path resolution, filtering, and atomic-publish bookkeeping around those two calls. The premise holds.

verified   BuildProjectGraph genuinely invokes the real binary for real work

Nothing in internal/graphify is stubbed or mocked in the shipped tests. Every test builds an actual temporary git repository with real committed files, then BuildProjectGraph shells out to the real graphify binary via the unmocked runCommand package variable (mocked only in the specific tests that exist to record invocation counts, and even then by wrapping — not replacing — the real call). I ran the suite myself; per-test wall-clock time (0.3–0.6s for extraction of a one-file repo) is consistent with a real subprocess invocation, not a canned mock response.

verified   The zero-participating-repos guard is real, confirmed by my own mutation

The commit message's specific claim — that the original test only asserted err != nil, which a missing guard would still satisfy indirectly via graphify merge-graphs's own zero-input rejection, and that the fix strengthened the assertion to zero subprocess invocations — is accurate. I disabled the guard myself (commented out the early return in BuildProjectGraph) and reran TestZeroParticipatingReposIsBuildError: it failed with "expected no graphify invocations ... got: [[graphify merge-graphs --out ...]]" — exactly the failure the strengthened assertion exists to catch. Reverted cleanly.

One residual, non-blocking nuance: the "zero invocations" assertion is strong against this implementation shape (which always reaches the merge-graphs call when len(repoGraphs) != 1, including zero). A hypothetical future refactor that special-cased zero repos to skip straight to writing an empty/missing graph.json without any subprocess call would pass the "zero invocations" check while still being wrong — though the build's own "merged graph is missing or empty" check immediately downstream would still catch that case and still return an error either way, so the required behavior (zero repos is a build error, nothing gets published) would still hold under that hypothetical. Not a defect in the current code; noted because the task explicitly asked whether an even sneakier regression could hide behind this specific assertion.

verified   Atomic publish (no partial read) is real, confirmed by my own mutation

TestBuildNeverLeavesOutputInAPartialState does prove what it claims, not just "old content survives." It uses a real concurrency setup — a publishHook seam that pauses a second, real BuildProjectGraph call mid-flight via a goroutine and a channel, while the main goroutine reads Output and asserts it is byte-for-byte identical to the prior graph. I mutated the publish ordering myself: moved os.RemoveAll(proj.Graphify.Output) to run before the publishHook pause instead of after it — a real non-atomic sequencing, since it creates a window where Output is deleted but the new content is not yet renamed in. The test failed immediately ("no such file or directory" reading the mid-flight graph), proving the test does detect a broken publish order and is not merely checking end-state. Reverted cleanly.

warn   The publish step has no crash-safety or cross-filesystem safety net, unlike v1's design it claims to reimplement

BuildProjectGraph's publish step is os.RemoveAll(Output) followed by os.Rename(scratch, Output), with no recovery path if the process dies, is killed, or the Rename itself fails, between those two calls. If Rename fails — which happens whenever the source and destination are on different filesystems (EXDEV), since scratch is created via os.MkdirTemp("", ...) under the system default temp directory ($TMPDIR//tmp) with no guarantee it shares a volume with the operator-configured Graphify.Output — the prior published graph has already been deleted by RemoveAll and is not recoverable; the build simply returns an error having destroyed the only copy of the graph. v1's sgt-graphify, which this proposal explicitly says it reimplements "the same stage-verify-then-rename shape," in fact does more: it moves the old output aside to a backup path (mv, not delete) rather than removing it, stages a _publish_parent_for_output helper specifically so "the final rename never crosses filesystem boundaries" (v1's own header comment), and registers an EXIT trap (_restore_old_output) that restores the backup on any failure path. None of that survived the port to Go. On this development machine the risk is currently masked: macOS APFS firmlinks put /tmp, $TMPDIR, and $HOME on the same device (confirmed via os.stat().st_dev), so Rename never actually crosses a filesystem boundary here — which is also almost certainly why the existing tests never surface this, since t.TempDir() for both scratch and output land on the same volume. But a different disk, a tmpfs /tmp on Linux, or an external/network volume configured as graphify.output would hit this. This is a real regression in operational safety against the system being ported from, not something the proposal disclosed as an accepted gap, and not something any test in this bullet exercises.

verified   exclude_patterns is disclosed-unapplied, not silently half-done

config.Graphify.ExcludePatterns exists, is documented in its own doc comment as "parsed and stored but not yet applied by BuildProjectGraph," and a full grep of internal/graphify/ for ExcludePatterns returns zero hits. The proposal's "Out of scope" section names this explicitly. The claim matches the code exactly.

verified   MCP tools and the HTTP endpoint refuse cleanly on a missing graph, with real invocation-count proof

requireGraph in query.go stats graph.json before any subprocess is spawned and returns ErrNoGraph if it is missing or empty. This is exercised at two layers, both with counters on the real runCommand seam rather than just checking an error string: TestQueryWithNoGraphBuiltIsAClearError in internal/graphify and TestMCPGraphToolsWithNoGraphBuiltReturnClearError in internal/mcp (the latter also asserts the output directory is never created). Both pass.

verified   Scope discipline held: no CLI, no dashboard UI, no report/cluster/watch code touched

git show 8a2eb22 --stat shows only internal/config, internal/graphify, internal/mcp, and internal/ui/server.go changed — nothing under cmd/. A repo-wide grep of dashboard HTML/JS for graphify or build-graph returns nothing. POST /api/build-graph is the only new trigger, exactly as the proposal's "Out of scope" section requires. No GRAPH_REPORT.md, clustering, graphify watch, or global-graph code exists anywhere in this diff.

bad   "Must not call sgt-graphify" is true of the code this bullet added, and false of the system as currently built and configured

The commit message states, without qualification, that "no sgt-graphify process is ever spawned" — proven, it says, by TestBuildNeverSpawnsSgtGraphify. That test is real and does prove that internal/graphify.BuildProjectGraph never spawns it. But it is not the only code path in this repository that can spawn sgt-graphify. cmd/sergeant-mcp/main.go — a separate MCP stdio server, first added in commit 347e2c7 well before this bullet, and not touched by this merge — is a generic wrapper that exposes every bin/sgt-* v1 shell script as its own MCP tool, one of which is registered by name as scriptName: "sgt-graphify", toolName: "sgt-graphify" (lines 248–249). It is not dead code: mise.toml's [tasks.build] builds it (go build -o bin/sergeant-mcp ./cmd/sergeant-mcp/) every time bin/sergeant is built, and mcp.json declares it as a live server named "sergeant" alongside the new native server named "sergeant-v2". Any agent client configured against the "sergeant" server — which is the first and, per mcp.json's ordering, arguably the default-looking one — can call a tool named sgt-graphify and have it shell directly to v1's bash script, in direct contradiction of D9's own text ("must not call sgt-graphify (D7)") and of AGENTS.md's "v1 is not a dependency" section, whose listed prohibition ("do not call sgt-dispatch, sgt-watch, sgt-respond, sgt-validate, sgt-context, or any other bin/sgt-* script") already covers this by its own "or any other" clause. This predates the bullet under review and is not a regression this merge introduced — but the merge's own claim of proof ("no sgt-graphify process is ever spawned") is stated with a confidence the actual system does not support, and no finding in this proposal or the merge commit discloses that this second, older MCP surface exists or that it still offers exactly the thing D9 forbids. This is the single most important finding in this review: it means D9's decision text is not actually enforced system-wide, only inside the one new code path built to satisfy it.

warn   The codesign fix that unblocked this dispatch is real but entirely manual, with nothing in the build tooling to reapply it

codesign -dv ~/.local/share/sergeant-v2/bin/sgt-p confirms Identifier=dev.sergeant.ui, matching the commit's claim exactly, so the diagnosis and fix for this cycle's dispatch failures appear to be real. But I grepped mise.toml and .goreleaser.yaml for codesign and found nothing — the stable identifier is applied by a one-off manual command the commit message documents in prose, not by any build task. The commit message itself says this "must be applied after every future rebuild of this binary." Nothing in the repository enforces that. The next person (or agent) who rebuilds bin/sgt-p without knowing this history will silently reintroduce the exact TCC hang that cost 4 prior dispatch attempts, with no test or CI check that would catch it before a headless launchd run hangs again.

Verdict

D9 Task 1: partly met — genuinely met for the code this bullet added, only apparently met for the decision as a whole. The scoping correction the proposal opens with is not spin: I independently confirmed the real graphify binary exists, does the actual extraction and graph-algorithm work, and that v1's sgt-graphify really is nothing more than bash orchestration around it. "Native" genuinely means what the proposal says it means here — Go code owns orchestration, configuration, and publication, while the real external tool still does the graph work — and that framing holds up under scrutiny, not just under its own restatement. BuildProjectGraph really invokes the real binary in its tests, not a stub. The two properties the commit message singles out for extra proof — the zero-participating-repos guard and atomic, no-partial-read publishing — are both genuinely tested, and I confirmed both myself by breaking each one with my own mutation and watching the corresponding test catch it, then reverting. exclude_patterns is honestly disclosed as unapplied rather than silently dropped. The three MCP tools and the one HTTP trigger are thin, correctly-scoped wrappers that refuse cleanly — with real invocation-count proof, not just an error string — when no graph has been built. No CLI subcommand or dashboard element was added, honoring the proposal's explicit exclusions.

Two things keep this from a clean "genuinely met." First, and most important: the decision text's actual, load-bearing requirement — "must not call sgt-graphify" — is not true of this system as built and configured, only of the one new code path built to satisfy it. cmd/sergeant-mcp, unrelated to this bullet's diff but still actively built and still declared in mcp.json alongside the new server, exposes a tool literally named sgt-graphify that shells straight to v1's script. The commit's claim that "no sgt-graphify process is ever spawned" is true of internal/graphify and false of the repository as a whole, and nothing in the proposal or the merge discloses this. Second, the atomic-publish implementation quietly dropped the crash-safety and cross-filesystem guarantees v1's own version of "the same stage-verify-then-rename shape" actually had (backup-and-restore on failure, same-filesystem staging) — a real regression, currently masked only by this machine's single-volume APFS layout putting /tmp and the output directory on the same device.

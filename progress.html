Findings

verified   The migration is real and complete on both paths

createIntentsTable (fresh DB) and migrateAddColumns (existing DB) were both updated in lockstep: change_id TEXT NOT NULL DEFAULT '' and change_repo TEXT NOT NULL DEFAULT '' appear in the CREATE TABLE DDL and as two new ALTER TABLE intents ADD COLUMN entries in the migration table, with a doc comment correctly noting existing rows "predate plan approval and have nothing to backfill." A store opened against a database created before this commit would pick up both columns via the migration path; a store created fresh already has them. I did not just read this — I ran the full internal/store and internal/ui suites, which exercise fresh-DB creation via store.Open in every test's temp directory, and they all pass, which would not be true if the DDL and the Go struct/scan code disagreed on column count or order.

verified   No query against the intents table was missed

All four functions that touch intent rows by column list — CreateIntent (INSERT), GetIntent, ListIntentsForProject, ListIntentsByStatus (all SELECT) — read or write both change_id/change_repo, each SELECT wrapped in COALESCE(..., '') so a pre-migration NULL (there shouldn't be any, given the NOT NULL DEFAULT '' column, but the existing statement column gets the same defensive treatment) can never surface as a Go zero-value scan error. UpdateIntentStatus was correctly left alone — approval only ever changes status, never the change identity, so this is the right scope, not an oversight.

verified   Proposal-time capture uses already-resolved values, not a second resolution

handleDispatch resolves changeRepoName/changeRepoPath/change once, unconditionally, before branching on len(req.Repos) == 0 (decision O3's ordering). The no-repos branch's new CreateIntent call reads change.ID and changeRepoName straight out of those already-computed local variables — there is no second call to changeRepo or resolveChange anywhere in this branch. This is exactly the "durable capture at the point of first resolution" the commit message claims.

verified, mutation-tested   Approval reuses the captured change verbatim; I independently broke and restored the fix

handleApprovePlan's changeRepo(proj, targetRepos) call is gone. In its place: changeRepoName := intent.ChangeRepo, a direct proj.Repos[changeRepoName] lookup with an explicit !ok || strings.TrimSpace(repoCfg.Path) == "" guard, and resolveChange(changeRepoPath, intent.ChangeID, intent.Statement) — intent.ChangeID where the old code passed a literal "". I did not stop at reading this. I reverted both lines back to their pre-fix form (changeRepo(proj, targetRepos) / resolveChange(changeRepoPath, "", intent.Statement)), rebuilt cleanly, and reran TestApprovingAPlanReusesTheOriginallyResolvedChangeNotASecondOne. It failed on both assertions: the dispatched run's ChangeID came back as a-totally-different-brief-text (re-derived from the brief) instead of the proposed add-stripe-webhooks, and openspec/changes/ held three entries (a-totally-different-brief-text, add-stripe-webhooks, archive) instead of one — a second change directory really was scaffolded, exactly as the commit message describes. I then restored the file with git checkout -- internal/ui/server.go and confirmed git status --porcelain was empty before continuing.

verified   The regression test's brief/change_id pair cannot pass the bug by accident

The commit message states this exact false-negative happened once during development. I checked it myself rather than taking that on faith: deriveChangeID lowercases the brief and joins runs of [a-z0-9] with single hyphens, dropping everything else. Applied by hand to "a totally different brief text", the result is a-totally-different-brief-text — seven hyphen-joined words, none of which is add-stripe-webhooks's add/stripe/webhooks. Since the two ids are unmistakably different, a mutant that re-derives the change id from the brief instead of reusing intent.ChangeID is guaranteed to produce a different, wrong id — which is exactly what the mutation test above observed.

verified   The repo-removed-before-approval edge case degrades cleanly, not with a panic

Task item 4 asked what happens if proj.Repos[intent.ChangeRepo] no longer exists at approval time — e.g. the project YAML is edited between proposal and approval to drop that repo. The fix's guard (!ok || strings.TrimSpace(repoCfg.Path) == "") handles this explicitly: I wrote a throwaway test that proposes a plan against the fixture's only repo (svc), rewrites the project's YAML file (located via $SERGEANT_CONFIG) to remove svc entirely and add an unrelated repo, then approves, with a recover() around the HTTP call to catch any panic. Result: no panic, HTTP 500, body plan "sgt-…-intent"'s change repository "svc" is no longer configured in project "o3" — a legible, actionable message naming the plan and the missing repo, not a generic nil-pointer crash. Deleted the throwaway file afterward (git status --porcelain confirmed clean).

verified   No second instance of "recompute instead of reuse" found in the plan-approval flow or its siblings

Task item 5 asked whether anything else in the propose→approve→dispatch path is re-derived at approval time instead of carried from proposal time, using bullet order as a candidate. Tracing it: bullets are written with an explicit Position: i+1 at creation time (both in the no-repos proposal branch and in createRunAndDispatch's explicit-repos branch), and ListBulletsForIntent reads them back ORDER BY position ASC, created_at ASC, id ASC — a durable value written once and read back by that same value, not recomputed from some other input. handleApprovePlan builds targetRepos by iterating that already-ordered result in one pass, and createRunAndDispatch skips its bullet-creation block entirely when reusing an existing intent, so the original Position values are never rewritten. This was already the correct pattern before this commit (Review 020 confirmed the same thing) and remains so. I also checked the two sibling OpenSpec changes in the tree, a-stuck-bullet-is-blocked-not-failed and graphify-honors-exclude-patterns: neither touches the propose/approve time gap this fix closes — one governs bullet terminal status (blocked vs. failed), the other governs graphify's file exclusion during graph merge — so there is no overlapping instance of the pattern in either.

Verdict

MEETS SPEC. This closes D5a's remaining gap (Review 020's finding) cleanly. store.IntentRecord durably records the OpenSpec change (id and repo) at the moment it is first resolved — either immediately for an explicit-repos dispatch's own bookkeeping non-use, or at proposal time for a no-repos dispatch — via a real, correctly-ordered migration and consistent read/write across every query against the intents table. handleApprovePlan no longer calls changeRepo or resolveChange with fresh or empty inputs; it reuses intent.ChangeRepo/ intent.ChangeID verbatim, with an explicit, panic-free guard for the case where the recorded repo is no longer configured by approval time. I independently confirmed the regression test is load-bearing (its brief and change_id cannot coincidentally slugify to the same value), independently broke the fix and watched the test fail with the exact predicted symptom on both assertions, and independently restored it to a byte-identical working tree. I found no second instance of the same "recompute instead of reuse" pattern elsewhere in the plan-approval flow or its two sibling in-flight changes. The one incidental issue I hit — a single flaky failure in an unrelated internal/graphify test — traces to a different, pre-existing commit and is not reproducible; it does not affect this verdict.

Verdict: R5.3 is genuinely met — durability and the append-only history are real, not just claimed. R5.4 is only partly met: bounded retry, an application+DB-enforced idempotency key, and explicit states are real and correctly wired at both call sites. But two things R5.4's own text names as required delivery metadata are absent from the actual data: the next_attempt_at column is written for every row and is always NULL, including on retrying rows, contradicting this change's own design doc; and there is no error classification anywhere — only a raw, unclassified error string. Neither is disclosed as deferred in proposal.md's "out of scope" list, which only defers dead-lettering, an ack protocol, and operator surfaces. This is the "green tests, quietly incomplete requirement" pattern this project has hit before, just one level more subtle than last time: the code that exists is correct, but part of what R5.4 asked for was never written and nothing failing calls that out.

Findings

high   next_attempt_at is never populated — contradicts this change's own design doc and R5.4's text

design.md states plainly: "the delivery transitions to retrying with next_attempt_at set". It is not set. insertDeliveryRow's INSERT statement never lists the column, on any state, including retrying:

internal/store/delivery.go:99-104
INSERT INTO deliveries
 (id, envelope_id, consumer, state, attempt, error, idempotency_key, created_at, updated_at)
 VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)
                              ^ next_attempt_at is a real column; it is not in this list, ever

verified live (throwaway test, reverted):
  state=pending   next_attempt_at=NULL error=""
  state=retrying  next_attempt_at=NULL error="fail once"
  state=delivered next_attempt_at=NULL error=""

R5.4's own text requires "lease/next-attempt timestamps" as part of what a delivery record carries. proposal.md's out-of-scope list defers dead-lettering, the ack protocol, and operator surfaces — it does not defer this field. No test in delivery_test.go asserts on NextAttemptAt at all, so nothing in the merged suite could have caught this. This is not a design tradeoff that was made and documented (the "no sleep between retries" tradeoff in design.md is explicitly documented and reasonable); this is the documented design not matching the shipped code, on a field the requirement names explicitly.

medium   No error classification anywhere — only a raw error string

R5.4: "... consumer identity, and error classification." delivery.go has one error TEXT column, populated with lastErr.Error() verbatim. There is no enum, tag, or derived category (transient vs. permanent, I/O vs. validation, etc.) anywhere in the file — confirmed by grep -n "class\|Classif" internal/store/delivery.go, zero hits. A raw message is useful to a human reading the row, but it is not a classification, and nothing computes one. This may be intended to land with bullet 3 (dead-lettering, which needs a "reason" per R5.5), but proposal.md does not say so — it is simply absent from both the proposal's scope and its out-of-scope list.

medium   The DAG-engine call site is correctly wired but has zero test coverage in the merged commit

The commit's whole stated reason for existing is closing "green tests coexisting with an unwired production call site" — and it did close that, but only for one of the two call sites it names. TestAgentPhaseRecordsDurableDelivery genuinely exercises runner.RunAgentPhase end to end. No equivalent exists for dag.Engine.RunStage's DeliverEnvelope-wrapped InjectHandoffToWorktree branch:

grep -rn "\.After\b" internal/dag/*.go internal/config/*.go
  internal/config/config_test.go:63-64   <- only tests YAML parsing of After
  internal/dag/engine.go:281             <- for _, upstream := range stage.After (the code under test)
  (no dag test ever sets stage.After, so this branch never runs in CI)

I wrote a throwaway test (two upstream/downstream repos, a pre-recorded upstream envelope, stage.After = []string{"upstream"}) and confirmed the branch works correctly: the delivery reaches delivered, and the file lands under .sergeant/handoff/upstream/ in the downstream worktree. So this is not the CausationID bug recurring — the code is right — but it shipped unverified by anything in the suite, on the exact call site the commit message singles out by name. The next person to touch this branch has no regression test protecting them.

low   "Reuses the R2.4 retry ceiling" overstates what actually happened

The commit message and design.md both frame deliveryMaxAttempts = 3 as reuse of "the retry ceiling already resolved for R2.4 ... rather than inventing a second one." config.Project.ResolvedRetries is a per-project, YAML-configurable value with no fixed default of 3 baked in, and delivery.go never calls it — deliveryMaxAttempts is an independent, hardcoded const. The number happens to coincide with a plausible R2.4 value; the mechanism is not shared, and a project that configures R2.4's retries to something other than 2 (giving 3 total attempts) now has two retry ceilings that can silently diverge. Not a functional defect — a second ceiling is a legitimate design choice, just not the one described.

verified   R5.3 — durability and append-only history are real

The deliveries table is genuinely insert-only: no UPDATE statement touches it anywhere in the package. A pending row is provably written before the wrapped attempt resolves — TestDeliveryPendingRowExistsBeforeOutcomeKnown blocks the attempt mid-flight on a channel and reads the row while it is still pending, which is a real concurrency test, not a sequencing assumption. Migration is wired correctly for pre-existing databases via migrateAddTables, confirmed by reading store.go:331-336.

verified   Both real call sites are actually wired, not just present in the diff

This is the exact bug class the review brief asked to hunt for again (after the earlier CausationID incident), and it did not recur in the same shape. In runner.go, deliverErr is captured separately from the agent's own lastErr and returned from RunAgentPhase on the success path (runner.go:496-498); that return is not swallowed by dag/engine.go:352-355, which wraps it and returns it up through RunStage. In engine.go, the DeliverEnvelope-wrapped injection's error is returned directly (engine.go:291-295). Neither site discards the error with _ = anymore, and I traced both all the way to their eventual caller rather than stopping at the call site itself.

  -> FAIL TestDeliveryRetriesUpToBound
  -> FAIL TestDeliveryThreeAttemptsShowsFullHistory

Worth naming precisely: the idempotency guarantee here protects the record (a second delivery cannot be recorded as delivered twice) via a DB-level partial unique index as backstop behind the application check — described accurately in the code's own comments as closing a check-then-insert race. It does not, by itself, prevent the wrapped attempt() side effect from running twice if two callers raced for the same key before either reached the terminal insert; the second caller's attempt() would still have run before its delivered row is rejected. This is not exploitable today because both real call sites run synchronously, single-goroutine, inside one phase's execution — but it is a latent gap if this mechanism is ever reused by a concurrent caller, and it is worth naming now rather than rediscovering later.

Matches tasks.md: dead-lettering, replay/quarantine, and CLI/UI/MCP operator surfaces are correctly left for bullets 3 and 4. acknowledged is in the state vocabulary but nothing drives a row to it, exactly as proposal.md discloses.

verified   Simpler than v1's mechanism, and a fair simplification for now

v1's _sgt-response-lock.sh gets its idempotency guarantee from an flock'd directory plus an archived proof record matched on response id, gate generation, and applied status — real, but bespoke to one handoff and unqueryable as a set. v2's mechanism is one general table any consumer can use, backed by the same store as everything else, which is the right direction for a Go-native rewrite. v1's sgt-msg-* family (also SQLite-backed) has no retry/backoff/dead-letter concept at all — v2's state machine and bounded retry are new capability relative to v1, not parity work. The design doc's rejection of a background outbox dispatcher for two synchronous, in-process call sites is reasonable and explicitly argued, not just asserted.

Verdict

R5.3: genuinely met. Append-only, durably persisted before acknowledgement, survives process exit in the sense that matters (it is a committed SQLite row, not in-memory state) — verified by reading every write path and by a real concurrency test, not by trusting the test suite's name.

R5.4: only apparently fully met. State machine, attempt counting, consumer identity, bounded retry, and a derived idempotency key are real and correctly wired at both call sites named in the commit message. But two things R5.4's own sentence requires — lease/next-attempt timestamps and error classification — are not actually produced by the shipped code, and nothing in the 409-line test file would have caught either absence, because nothing asserts on those fields. The green suite proves the parts of R5.4 that were tested, not all of R5.4.

Severity-ranked: (1) next_attempt_at always NULL, contradicting the change's own design doc — high, because it is a factual claim in the design doc that is simply false against the shipped code, on a field the requirement names by name; (2) no error classification — medium, plausibly deferred to bullet 3 but not stated as such; (3) the DAG-engine call site's total lack of test coverage — medium, because it is exactly the class of risk this commit exists to close, just not fully closed; (4) the "reuses R2.4's ceiling" claim and the record-level-only idempotency guarantee are both low severity — accurate enough in practice today, worth naming, not worth blocking on.

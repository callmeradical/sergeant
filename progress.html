Findings

high   The new MCP tools cannot be reached by any client

The native server exposes all 7 tools including the two built for following a run. But mcp.json — the file a client reads — names ./bin/sergeant-mcp, which does not exist. A client using the documented config starts no server at all.

$ printf '...tools/list...' | sergeant mcp
   sergeant_status
   sergeant_get_brief
   sergeant_run_gates
   sergeant_emit_envelope
   sergeant_seal_pr
   sergeant_run_status      <- new
   sergeant_run_wait        <- new

$ cat mcp.json  ->  "command": "./bin/sergeant-mcp"
$ ls -la bin/sergeant-mcp  ->  DOES NOT EXIST

The requirement "an agent can follow a run it dispatched" is implemented and tested at the Go level and undeliverable at the integration level. I previously reported this as "MCP follow tools live". That was wrong: live in the binary, dead in the configuration. Related to the held item A1 (td-ccc18b), whose hold now has a measurable cost.

high   Nothing advances an intent or a bullet, so the primary table is wrong by design

Dispatch now creates intents and bullets (D4). Nothing ever updates them. UpdateIntentStatus and UpdateBulletStatus have no production callers — only their own definitions and tests.

intents:  in_progress 4   satisfied 2     <- the 2 were set by hand, in SQL
bullets:  pending     4   merged    4     <- the 4 merged were set by hand, in SQL

Every run that finishes leaves its intent at in_progress forever, including runs that passed and runs that were cancelled. D8 makes the intent the dashboard's primary object, so the primary object will show a status that is false for most rows. This is worse than the pre-D4 state: an empty table was honestly empty, whereas a table of permanently in_progress intents asserts something untrue. That conflicts with the standing rule against displaying a value not derived from stored state.

medium   Every SSE snapshot ships 31 KB, most of it prompt text

Measured: 31,304 bytes for a snapshot at 30 runs. The payload embeds each run's full brief, and briefs here are multi-paragraph agent prompts. Sent on first connect and on every reconnect or unknown-sequence recovery.

Correct but it grows without bound with run count, and it is the exact path a flaky connection retries. The run list does not need the brief; the drawer can fetch it per run.

medium   The whole working tree is served over the tailnet

This page is served by python3 -m http.server 8787 with cwd /Users/lars/Dev/sergeant-v2, proxied by tailscale from :4387. Directory listing is on and source is readable.

/                      -> HTTP 200  (directory listing)
/internal/ui/server.go -> HTTP 200
/.git/config           -> HTTP 404  (worktree: .git is a file, not a dir)

Tailnet-only, and no git history is exposed, so this is hygiene rather than an incident. Serving a dedicated directory holding only this page would remove it.

medium   One OpenSpec change is stuck and cannot archive

serve-the-workflow-as-a-graph-definition-per fails validation: no delta specs, no scenarios. Its implementation was merged long ago. The change directory holds only .openspec.yaml.

Chain of custody is the stated reason OpenSpec was adopted (§3b). A merged change with no spec is precisely the undocumented work it exists to prevent. Either write the delta specs or set skip_specs: true with a reason.

Blockers

Nothing is blocked on a decision by me. One item needs an owner's call: A1 / td-ccc18b is held pending graphify, and that hold is what leaves mcp.json pointing at a non-existent v1 proxy. The native server is ready now, so the hold's cost is that a merged, tested capability is unreachable. Holding remains legitimate; it should be a decision rather than an oversight.

Next action

In order, highest severity first:

1. Repoint mcp.json at the native server. Change the command to the built sergeant mcp subcommand, or build bin/sergeant-mcp from the native path. Verify by listing tools through the config a client would actually load, not by running the binary directly — that is the check that would have caught this.
2. Advance intents and bullets from the run lifecycle. A run reaching a terminal state should move its intent and bullets. Needs a decision on the mapping first, particularly whether a passed run means satisfied or only green, since merging is still a human act (D6). Do not backfill the 4 stuck rows by hand again; the fix is the missing transition, not the rows.
3. Resolve the stuck OpenSpec change — write its delta specs or record a skip_specs reason.
4. Drop brief from the stream snapshot and fetch it per run in the drawer.
5. Serve this page from its own directory rather than the repository root.

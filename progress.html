Findings

verified   Node/link/hyperedge exclusion by source_file, then dangling-reference cleanup, is exactly as design.md specifies

filterGraphFile makes two passes conceptually within one loop each: first, an element is dropped outright if its own source_file matches any configured pattern (nodes recorded into survivingIDs only if kept); second, for links and hyperedges whose own source_file did not match, a further check drops them if they now reference a node id that filtering just removed (links: either endpoint missing; hyperedges: fewer than 2 of their listed node ids still present). This exactly matches all three scenarios in specs/graphify-exclusion/spec.md's first requirement. The shipped test TestDanglingLinkAndHyperedgeAfterNodeExclusionAreRemoved constructs precisely this case — a link/hyperedge whose source_file is keep.go but whose target node's source_file is drop.go — and asserts both are absent, not merely that no error occurred.

verified, mutation-tested independently for both branches   Dangling-reference cleanup is real code, not a test artifact of coincidental ordering

I did not trust the shipped mutation coverage (there was none demonstrated in the diff) — I performed two independent mutations myself. First, I deleted the link-side check entirely (if !survivingIDs[l.Source] || !survivingIDs[l.Target] { continue }) and reran TestDanglingLinkAndHyperedgeAfterNodeExclusionAreRemoved: it failed, reporting the dangling link ({n1 n2 keep.go}) present when the test expects it absent — exactly the predicted symptom. I restored the file with git checkout and confirmed git status --porcelain and git diff --stat were both empty. Second, and separately, I changed the hyperedge threshold check from if remaining < 2 to if false (so it never drops a hyperedge for having too few surviving endpoints) and reran the same test: it failed again, this time reporting the dangling hyperedge ({[n1 n2] keep.go}, only 1 real endpoint) present. Restored and reconfirmed a clean tree both times. Both halves of the dangling-cleanup logic are load-bearing, not dead code the test would pass without.

verified   */** glob semantics are correct, including on inputs the shipped test suite does not cover

matchSegments splits both pattern and candidate path on / and recurses: a "**" segment tries consuming zero segments first (recurse with the rest of the pattern unchanged against the full remaining name), then backtracks to consume one name segment at a time if that fails — correctly modeling "any number of segments, including zero." A non-"**" segment is matched one-for-one against exactly one name segment via path.Match (which already handles */?/character classes within a segment), and the recursion's base case (len(pattern) == 0) requires len(name) == 0 too — so a pattern with no ** at all necessarily requires an exact segment count match. I wrote 12 of my own test cases in a throwaway file (deleted after, tree confirmed clean) beyond the 3 patterns the shipped suite exercises (drop.go, exact match; vendor/**, directory-recursive): a/**/b correctly matches both a/b (zero segments consumed) and a/x/y/b (two segments consumed) but not a/x/b/c (trailing segment after the required b); **/*.go matches main.go sitting at the repository root (zero directory segments before the file); a/b (no **) correctly rejects both a/b/c (too many name segments) and, symmetrically, a/b/c as a pattern rejects a/b as a name (too few). All 12 passed on first run.

verified   Every unrecognized field, at every level, survives filtering — the shipped implementation is stronger than design.md's own sketch

The top-level graph.json document is parsed as map[string]json.RawMessage, so keys other than nodes/links/hyperedges (e.g. directed, multigraph, graph, built_at_commit) are never touched. More significantly, each individual node/link/hyperedge is also carried as a whole json.RawMessage through the keep/drop decision — the small anonymous structs in filterGraphFile (struct{ ID, SourceFile string } etc.) exist purely to read the two or three fields the filtering decision needs; they are never re-marshaled back out. This means a per-element field the design doc's own pseudocode sketch (which used typed Node/Link/Hyperedge structs with only the fields the pass touches) would have silently dropped on round-trip is, in the shipped code, preserved by construction — the shipped implementation deviates from design.md's own sketch, for the better, on exactly the point tasks.md calls out ("do not round-trip through a struct that silently drops unknown keys"). The shipped test TestEmptyExcludePatternsIsStructuralNoOp proves this directly: its fixture carries 4 unrecognized top-level keys and 3 unrecognized per-element fields (extra_field, weight, relation), and the test asserts reflect.DeepEqual between the fully-parsed interface{} tree before and after filtering with both nil and {} patterns — a structural-equality assertion, matching tasks.md's explicit requirement to check "byte-for-byte or structurally, not just no error."

verified   The empty-patterns case runs the real code path, not a bypassed branch

Design.md's own pseudocode sketch included a special case (if len(patterns) == 0 { return rewriteGraphFile(path, readGraphFile(path)) }) — a distinct, separately-exercised no-op branch. The shipped code has no such branch: matchesAny called with an empty patterns slice simply never matches anything, so every node/link/hyperedge survives via the exact same loop used when patterns are present. This is a stricter reading of design.md's stated intent ("the same 'empty means everything' convention... always run the real code path with a no-op input") than design.md's own sketch would have delivered literally. TestEmptyExcludePatternsIsStructuralNoOp exercises both nil and []string{} and gets identical, structurally-verified results for both.

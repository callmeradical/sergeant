Verdict: R5.1, R5.2 and R5.7 are genuinely met. This review exists specifically to hunt for the failure shape Review 007 found in bullet 2 — a store-level implementation that is correct in its own unit tests while a real production call site never actually wires the field. That exact bug does not recur here. I read the diff for every one of the four real, non-test call sites that publish an envelope in this codebase as of this commit (internal/mcp/server.go's sergeant_emit_envelope tool, internal/runner/runner.go's RunAgentPhase, and internal/ui/server.go's handleCreatePR and delivery-envelope write in executeRun), and all four set CorrelationID to the run id and CausationID to Store.CausationFromLatest(runID, repo) — a real lookup of the previously published envelope for that run/repo, called before the new envelope is recorded, not a hand-built test fixture. Immutability and the additive migration are both real and independently confirmed by tests I ran myself, and by one mutation I applied and reverted. I did, however, find a different real defect in the same "claims to do X, doesn't actually do X, nothing currently notices" family: the duplicate-id error classifier checks the wrong SQLite extended error code and can never actually match, detailed below. It does not break the immutability guarantee itself (the underlying INSERT still fails and RecordEnvelope still returns a non-nil error), so R5.1's required behavior holds — but the sentinel error the code claims to return is dead code, silently, and the bug is still present in current v2 HEAD.

Findings

verified   The unwired-call-site bug from Review 007 does not recur here

This is the headline question this review exists to answer. All 4 real, non-test call sites that publish an envelope in this codebase — internal/mcp/server.go's emit_envelope tool, internal/runner/runner.go's RunAgentPhase, and internal/ui/server.go's handleCreatePR and the delivery envelope in executeRun — set CorrelationID to the run id and CausationID to Store.CausationFromLatest(runID, repo), a genuine store lookup called immediately before each envelope is built, not a value only ever set in a hand-constructed test record. This is exactly the class of gap Review 007 found in bullet 2 (a real field that store-level tests covered but every production call site left unset); it is not present in this bullet.

verified   Immutability is real, confirmed by my own mutation

RecordEnvelope uses a plain INSERT (not INSERT OR REPLACE, unlike the pre-existing pattern for phases) into envelopes, whose id column is TEXT PRIMARY KEY, and returns ErrDuplicateEnvelopeID-wrapped (see below) or raw error on conflict, writing nothing. I edited the SQL myself to INSERT OR REPLACE in a scratch worktree, reran TestRecordEnvelopeRefusesRepublishOfExistingID, and it failed with "expected an error when republishing an existing id, got nil" — exactly the silent-overwrite the guard is supposed to prevent. Reverted with git checkout --; confirmed a clean tree and a successful rebuild.

warn   The duplicate-id error classifier checks the wrong SQLite code and can never match — ErrDuplicateEnvelopeID is dead code, and the bug is still present in current v2 HEAD

isDuplicateEnvelopeID returns true only when the driver error's extended code equals sqlite3.SQLITE_CONSTRAINT_UNIQUE (2067). But envelopes.id is declared TEXT PRIMARY KEY, not a separate UNIQUE index, and I confirmed empirically (a standalone probe against modernc.org/sqlite, then a throwaway test calling RecordEnvelope twice with the same id) that a duplicate insert into that column raises extended code 1555 (SQLITE_CONSTRAINT_PRIMARYKEY), not 2067 — even though the driver's own error text happens to read "UNIQUE constraint failed: envelopes.id", which is what makes this easy to miss on a read-through. isDuplicateEnvelopeID therefore always returns false for the exact case it exists to detect, and errors.Is(err, ErrDuplicateEnvelopeID) is never true for any caller, anywhere — I grepped the whole repository, at this commit and at current v2 HEAD, and no code calls errors.Is against this sentinel at all, so the bug is currently silent and has no observable behavioral consequence today: RecordEnvelope still returns the raw (unwrapped, less friendly) driver error, which is still non-nil, so the actual required behavior — refuse republication, write nothing — still holds, as confirmed by the mutation test above. This is not the specific "unwired call site" bug this review was sent to hunt for, but it is the same underlying failure shape: code that claims a specific, named behavior (classify this as a duplicate-id conflict and return a friendly sentinel) which is not actually reachable, and nothing in the green test suite notices because every existing test only asserts err != nil, never errors.Is(err, ErrDuplicateEnvelopeID) or the wrapped message text. I confirmed this same code, unchanged, is still present in current v2 HEAD (internal/store/store.go, isDuplicateEnvelopeID), inherited through bullets 2–4 with no later fix. Recommend either checking SQLITE_CONSTRAINT_PRIMARYKEY as well, or matching on the error text's "envelopes.id" substring alone (as the sibling isDuplicateRequestID already does for a genuine UNIQUE INDEX, where the code check is actually meaningful and correctly differentiates a run-id collision from a request-id collision).

warn   3 of the 4 real call sites have no call-site-level regression test for correlation/causation, only store-level tests and my own manual read-through

internal/runner/runner_test.go adds TestAgentPhaseEnvelopesChainCausation, which exercises RunAgentPhase end to end and whose own comment names exactly the risk this review was sent to check for. No equivalent exists for the MCP sergeant_emit_envelope tool (there is no internal/mcp/server_test.go at this commit at all — the package's only test files are config_test.go and run_follow_test.go, neither of which invokes emit_envelope) or for either of the two internal/ui/server.go sites (handleCreatePR, the delivery envelope in executeRun). I verified those three sites are correctly wired by reading the diff directly, and I stand behind that verification, but it is a real difference in test rigor between the one call site the builder specifically hardened against this class of bug and the other three, which rely on the store's own unit tests plus a human read-through. Given that Review 007's whole finding was exactly "the store's tests pass but a real call site doesn't do this," a codebase this deliberate about testing that exact risk in one place and not the other three is worth flagging even where, as here, manual verification did not turn up a defect.

verified   Additive migration is real, not just claimed

All 8 new columns are added through the established hasColumn-guarded ALTER TABLE ... ADD COLUMN pattern already used for prior additive migrations (bullets.pr_url, phases.attempt), each defaulting to '' except causation_id (left nullable) and the two DATETIME columns (defaulted to the zero-time literal). TestEnvelopeColumnsAddedOnReopen drops and recreates a pre-change envelopes table and confirms all 8 columns exist after reopening; and TestOlderEnvelopeReadsBackWithEmptyType seeds a raw pre-migration row and confirms it reads back with Type == "" and no error, not an invented value. Both pass. This is the one claim in this bullet that already had a dedicated test in the original commit, and it holds up.

verified   CausationID's absent-vs-empty distinction is real, with one disclosed and non-manifesting edge case

CausationID is a *string, backed by a nullable causation_id column (deliberately not NOT NULL DEFAULT '', unlike every other new text column). TestRecordEnvelopeFirstEnvelopeHasNoCausationID and TestOlderEnvelopeNullCausationIDIsNil both pass, at the direct read and at ListEnvelopesForRun. One caveat, disclosed in the code's own comment rather than hidden: causationIDValue/nullableText collapse a hypothetical non-nil pointer to "" into SQL NULL on write, so "something caused it but the id was not recorded" (a non-nil pointer to an empty string) is not actually distinguishable from "nothing caused it" (a nil pointer) if it ever occurred. The comment at the CausationID field declaration says exactly this: "that case is not representable in the current design." Since every id in this codebase is generated by fmt.Sprintf and is never empty, this never manifests in practice; noted as a known, accepted, and correctly documented limitation, not a hidden defect.

warn   factory_id, project_id and assignment_id from R5.1's reference list are not implemented, and the OpenSpec change does not say so explicitly

R5.1 names six reference fields "where applicable": factory_id, project_id, repo_id, run_id, phase_id, assignment_id. This bullet added only PhaseID (design.md: "the missing link in the reference chain; run and repo already exist"). FactoryID, ProjectID and AssignmentID are absent from EnvelopeRecord, and design.md's "added metadata" section does not explicitly say why — it only accounts for the fields it does add. On inspection this is a pre-existing, systemic gap rather than something this bullet introduced or was uniquely responsible for closing: there is no FactoryRecord type anywhere in the store, RunRecord.Project is a plain string rather than an id, and this codebase has no separate "assignment" entity distinct from a phase — a PhaseRecord already conflates the PRD's phase/assignment distinction. Given that, "where applicable" plausibly excuses the omission, and inventing three new id fields that reference nothing else in the system would not obviously improve correctness. Flagged as a documentation gap in the OpenSpec artifacts (they should say this explicitly) rather than an implementation defect.

Verdict

R5.1, R5.2, R5.7: genuinely met. EnvelopeRecord carries the metadata R5.1 names (short of three reference fields that are not modeled anywhere in this codebase, disclosed above, not unique to this bullet). RecordEnvelope genuinely refuses publication missing a type, schema version, producer, or correlation id, writing nothing on refusal — verified by the existing test suite, which I ran myself. Immutability is real and I confirmed it by my own mutation, not only by reading the test that claims it. The additive migration genuinely leaves pre-existing rows readable with an empty type rather than erroring or inventing one, confirmed by tests that simulate a real pre-migration schema. Most importantly for why this review exists: every one of the 4 real production call sites that publish an envelope sets CorrelationID to the run id and CausationID to the actual preceding envelope in that run/repo — the specific "store-level plumbing correct, production call site unwired" failure shape that Review 007 found in bullet 2 does not recur here. A different, lower-impact defect of the same general family was found instead: the duplicate-id error classifier checks the wrong SQLite extended error code and can never actually match, making ErrDuplicateEnvelopeID unreachable dead code — silent today only because nothing anywhere calls errors.Is against it, and not a break of R5.1's actual required behavior, which the underlying INSERT failure still delivers regardless of how the error gets classified. This bug is still present, unfixed, in current v2 HEAD and should be corrected there. A second, lower-severity gap: only 1 of the 4 real call sites (runner.go) has a regression test written specifically against the class of bug this review hunts for; the other 3 were verified by me manually, not by an automated test that would catch a future regression.

R5 overall (R5.1–R5.7, all four bullets): now fully independently reviewed, still not fully clean

All four R5 bullets have now received an independent critic review with live mutation testing: Review 007 found bullet 2 (bde2b2d) genuinely met for R5.3 but only partly met for R5.4 (next_attempt_at and error classification claimed set but never populated, undisclosed as deferred scope — that gap is not re-litigated here and stands as recorded); Review 008 found bullet 3 (d0edef7) genuinely met, with a test-rigor gap later closed by 189ad06; Review 010 found bullet 4 (806fb07) genuinely met; this review (bullet 1, 8e1c5e8) finds R5.1/R5.2/R5.7 genuinely met. The specific failure shape this project has now shipped at least twice — a green test suite covering store-level plumbing while a real call site or claimed field silently is not wired or does not work — was hunted for specifically in this review and was not found in the form Review 007 identified it (an unwired call site). A related instance of the same underlying failure shape (a claimed classification/behavior that is not actually reachable, unnoticed by a passing test suite because no test asserts the specific claim) was found instead, in the duplicate-id error classifier, with no current observable impact. Taken together: R5.3, R5.5, R5.6 hold up without reservation; R5.4 holds up only partially (Review 007's disclosed gap, unchanged); R5.1/R5.2/R5.7 holds up with two non-blocking findings recorded above. R5 as a whole should be read as fully and independently reviewed across all seven sub-requirements and all four bullets for the first time as of this review — but "independently reviewed" is not the same claim as "defect-free": R5.4's known gap and this review's duplicate-id classifier bug are both real, both currently unfixed in v2 HEAD, and both worth a follow-up commit before R5 is called closed without qualification.

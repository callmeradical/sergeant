Verdict: DOES NOT MEET SPEC. The choke-point architecture is genuinely sound for what it actually touches — Store.RecordPhase/RecordEnvelope really are the only production writers of their tables, the redaction really is load-bearing under mutation testing, and it really does protect call sites nobody has reviewed yet. But the commit's own motivating example — EnvelopeRecord.Artifacts in RunAgentPhase's agent-authored-envelope branch, named in the commit message as the "7th instance" — is not actually closed. It is closed for the row that lands in the database. It is not closed for the file that lands on disk, because that file is written by a different function, earlier in the same call, before the store's redaction ever runs. The choke point's own premise — "the one place every record passes through no matter which caller built it" — is false for this call site: Router.SaveEnvelope is a second, earlier choke point for the same content, and this commit did not touch it.

Findings

verified   The choke point is real: no code path bypasses Store.RecordPhase/RecordEnvelope to reach either table

I enumerated every .RecordPhase( and .RecordEnvelope( call in the repo and every INTO phases/INTO envelopes SQL literal in the repo. The only production writer of either table is internal/store/store.go; the one other raw INSERT INTO envelopes is a test fixture that deliberately bypasses RecordEnvelope to simulate a row written before a schema migration — an intentional, documented, test-only exception, not a second production path. This part of the claim is true, not aspirational.

verified   Both redaction blocks are load-bearing, and both actually generalize to call sites no prior review examined

Mutation testing confirms the code inside RecordPhase/RecordEnvelope is not decorative: disabling either block fails the corresponding shipped test on every assertion, and restoring it leaves git diff empty. I also built my own reproductions against two call sites this entire review lineage (Reviews 013–017) never once looked at — dag/engine.go's RecordRedExemption (a caller-supplied reason string, never redacted at its own call site) and ui/server.go's run-delivery envelope at line 1791 (built by describeDelivery from git remote/worktree state, a feature added for R5.6, not R4.4). Both came out redacted with a secret embedded, purely because they pass through the store — no call-site code, no awareness of redact at either site. This is exactly what "closes the guarantee for call sites that don't exist yet" is supposed to mean, and for the database it delivers.

bad   The commit's own "7th instance" is not actually fixed: the handoff file it also lands in bypasses the store entirely

RunAgentPhase's agent-authored-envelope branch (internal/runner/runner.go, around line 452 onward) reads an agent's own .sergeant/envelope.json into env. Before this commit, env.Artifacts was never redacted anywhere. The commit's stated fix is that RecordEnvelope now redacts Artifacts unconditionally, closing the gap "for call sites that don't exist yet." But look at the actual order of operations in RunAgentPhase:

env.Summary = redact.Text(env.Summary)      // redacted here, before any write
env.Payload = redact.JSON(env.Payload)      // redacted here, before any write
...
pr.Store.DeliverEnvelope(envelopeID, pr.RepoName, true, func() error {
    return pr.Router.SaveEnvelope(&env)      // writes env — including RAW Artifacts — to disk
})
...
_ = pr.Store.RecordEnvelope(&store.EnvelopeRecord{
    ...
    Artifacts: env.Artifacts,               // THEN redacted, in place, mutating the same backing array
    ...
})

Router.SaveEnvelope (internal/handoff/envelope.go) marshals env and writes it to <fleet root>/<run>/handoff/<repo>/envelope_<stage>.json and envelope_latest.json on disk. That write happens before RecordEnvelope ever runs. I reproduced this directly: a fake agent writes its own envelope.json with "artifacts":["API_KEY="+secret]; after RunAgentPhase returns, both handoff files on disk contain the raw secret verbatim:

envelope_build.json:  "artifacts": ["API_KEY=sk-abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOP"]
envelope_latest.json: "artifacts": ["API_KEY=sk-abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOP"]

Meanwhile the returned *handoff.Envelope and the persisted EnvelopeRecord.Artifacts both show [REDACTED] — which looks like proof the fix works, but is actually a side effect of Go slice aliasing: Artifacts: env.Artifacts in the EnvelopeRecord literal copies the slice header, not the backing array, so when RecordEnvelope writes e.Artifacts[i] = redact.Text(a) it mutates the exact same array env.Artifacts points at — after the disk file was already written from it. This is also why Review 017's own probes, which checked the returned value and the database row, did not catch it: both of those looked clean. The "protection" on the returned envelope is additionally contingent on RecordEnvelope actually reaching that line; its error is discarded (_ = pr.Store.RecordEnvelope(...)), so any early return from validation or a DB error would leave even the in-memory copy unredacted, with nothing to signal it.

The disk file does not stay put. internal/dag/engine.go:279–292 calls Router.InjectHandoffToWorktree for every downstream repo in a multi-repo run, which copies every file under the upstream repo's handoff directory — including the unredacted envelope_<stage>.json — verbatim into <downstream worktree>/.sergeant/handoff/<upstream repo>/. That path is inside a real git worktree. CommitRunOutput (internal/dag/engine.go:196–210) then runs git add -A unconditionally in that worktree with no code anywhere in sergeant seeding or checking a .gitignore entry for .sergeant/ — so whether the secret is swept into a real commit depends entirely on whether the target repository happens to already ignore that directory on its own. I did not run a full multi-repo dispatch through to an actual git commit to watch this land — that is a traced consequence from reading the code, not an executed reproduction — but the mechanism that would carry the secret from "unredacted file on disk" to "committed into the user's repository, PR'd, and pushed" is fully present and unguarded.

This directly contradicts the commit's stated scope. The commit message names this exact field (EnvelopeRecord.Artifacts) and this exact call site as the motivating "7th instance" the redesign was meant to close. It closes the database row. It does not close the file, because the file is written by a second, earlier function that touches the same data before the chosen choke point ever sees it.

residual, real but lower severity   The changes table is a third persisted-and-broadcast path with no redaction at all

PhaseRecord and EnvelopeRecord are not the only rows that get written and then handed to a client. internal/store/changes.go's AppendChange writes to the changes table, which /api/stream serves live over SSE — and it has zero redact reference anywhere in the file. Its one external caller, ui/server.go's appendRunProgress, reads each worktree's .sergeant/plan.json and forwards each item's Scenario field — free text sourced from a spec's #### Scenario: heading — directly into the broadcast payload. I reproduced this live: a plan.json with Scenario: "uses API_KEY="+secret lands in ListChangesSince's result with the secret intact, unredacted, and that is the same row /api/stream hands to every connected dashboard client.

I am calling this lower severity than the handoff-file finding because the content source is different: a spec's Scenario heading is normally human-authored project documentation, not raw agent/subprocess output, so a real secret landing there is less likely than in agent stdout or an agent-authored envelope. But the mechanism is exactly the R4.4 shape — free text flows to a persisted, broadcast destination with no redaction anywhere in the chain — and unlike the two functions this commit touched, nothing about the choke-point fix does anything for this table, because it structurally isn't a PhaseRecord or EnvelopeRecord.

residual, theoretical   redact.Text's heuristic does not catch a generic, non-API-key-shaped credential

redact.Text("https://svc-user:hunter2ProdDbPassword@github.com/example/svc.git") returns the string unchanged — none of redact.go's patterns (provider API key prefixes, bearer tokens, NAME=value lines) match a plain password embedded in a URL's userinfo. Not a regression from this commit — the same shape Review 016 flagged as the resolveGitRemoteURL edge case, and moving the redaction call site into the store does not change it: the heuristic itself has this scope regardless of where it is invoked from.

residual, carried forward unchanged from Review 016   handleBuildGraph still returns raw subprocess output in an HTTP error body

internal/ui/server.go's handleBuildGraph still does http.Error(w, err.Error(), http.StatusInternalServerError) where err can embed raw graphify extract/merge-graphs subprocess output with no redact call anywhere in the chain. Out of scope for this commit and unchanged since Review 016. Repeating it here only so it is not mistaken for a new gap or forgotten as an old one.

process note   Review 017 (commit 65f70fc) reached MEETS SPEC in good faith but with an incomplete sweep

Review 017 ran real mutation tests and two genuinely reproduced call-site probes — its work is not fabricated, and its conclusions about the store choke point itself are correct as far as they go. It did not open internal/handoff/envelope.go or trace what happens to an agent-authored envelope's Artifacts between the moment it is read off disk and the moment it is (or isn't) redacted, which is exactly where the blocking finding above lives. Verdict

DOES NOT MEET SPEC. The architectural move this commit makes is sound, and I verified that claim adversarially: every production write to the phases and envelopes tables genuinely goes through Store.RecordPhase/RecordEnvelope, the redaction inside both functions is genuinely load-bearing under mutation testing, and I built live reproductions against two call sites no prior review round had examined, both of which came out protected with no call-site-specific code at all. If the claim had been "this closes the class of bug for the database," it would be true.

But the claim, in the commit's own words, is broader: it names EnvelopeRecord.Artifacts in RunAgentPhase's agent-authored-envelope branch as one of the two concrete leaks this redesign exists to close. That specific leak is not closed:

  • Blocking: Router.SaveEnvelope writes the agent-authored envelope — including its raw, unredacted Artifacts — to a handoff file on disk before RecordEnvelope runs. The database row and the in-process return value both end up looking clean only because of an incidental Go slice-aliasing side effect, not because the content was actually redacted before it was persisted. The file itself, read directly after reproducing the scenario, still contains the raw secret.
  • Blocking, by traced consequence: that file is copied verbatim into every downstream repository's worktree in a multi-repo run, and nothing in sergeant prevents git add -A from committing it there, meaning the leak's ceiling is not "a row in a local sqlite file" but "committed into the user's actual repository and pushed via the existing PR flow" — a strictly worse outcome than any of the nine instances found across Reviews 013–016.

Two further findings are disclosed as residuals rather than blockers: the changes table (AppendChange) is a third, entirely unredacted persistence-and-broadcast path structurally outside PhaseRecord/EnvelopeRecord altogether, reproduced live with a secret in a plan.json Scenario field reaching the SSE stream — real, but the content source (spec text) makes a genuine secret less likely than in agent/subprocess output. And redact.Text's heuristic does not catch a generic (non-API-key-shaped) credential embedded in a URL — a pre-existing scope limitation of the heuristic itself, not new to this commit.

This review also corrects Review 017 (commit 65f70fc), which reviewed the same commit with real mutation tests and real call-site probes but reached MEETS SPEC because its sweep never opened internal/handoff/envelope.go. That commit stands in git history uncorrected in place — this entry supersedes its verdict rather than rewriting it.

The lesson is not "point-fix the handoff file too." The pattern across all review rounds so far is that every time a fix has been scoped to "the places I can see this value get used," something has found a place that wasn't checked. This round's version of that mistake is structural rather than a missed field: the redesign correctly identified that the database write path had many callers and one true choke point, but did not check whether the database write path was the only durable destination for the same in-memory value. It was not. Before trusting a choke point, enumerate every function that persists or transmits the same struct, not just every function that constructs it.

Findings

verified   The choke point is a genuine architectural closure, not a relabeled point-fix

The core claim under test was not "are Error/Payload/Summary/Data/ Artifacts redacted" — five prior rounds already answered variants of that question, each time for a specific call site. The claim that matters here is structural: does moving redaction into Store.RecordPhase/Store.RecordEnvelope actually protect call sites nobody has looked at yet, without anyone at those call sites remembering to call redact. I tested this directly against two call sites: dag.Engine.RecordRedExemption (a function with zero live callers wired to it in Review 016's own audit, and still none found in this review, but exactly the kind of code path a future feature could wire up) and the run-delivery envelope in internal/ui/server.go:1791 (a real, already-shipped, already-wired production path from a different PRD requirement, R5.6, that none of the five R4.4 fix commits or six review rounds ever inspected because it isn't part of the R4.4 lineage). Both leaked a live secret into a PhaseRecord/EnvelopeRecord field at construction time, and both came out clean after RecordPhase/RecordEnvelope, with no redaction call anywhere in either call site's own code. This is what "choke point" is supposed to mean, and it held.

verified   Both mutation tests prove the fix is load-bearing, not a comment next to unrelated code

Commenting out p.Error = redact.Text(p.Error) / p.Payload = redact.JSON(p.Payload) in RecordPhase makes TestRecordPhaseRedactsErrorAndPayload fail on all 4 assertions, with the raw secret visible in the failure output:

store_test.go:674: PhaseRecord.Error leaked the secret: "exited: sk-abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOP"
store_test.go:680: PhaseRecord.Payload leaked the secret: {"note":"sk-abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOP"}

Commenting out RecordEnvelope's Summary/Data/Artifacts-loop redaction makes TestRecordEnvelopeRedactsSummaryDataAndArtifacts fail on all 4 assertions the same way, including the Artifacts loop specifically — the exact field that caused the 6th and 7th instances in Review 016. Both mutations were restored exactly; git diff was confirmed empty after each restore, and both tests were rerun to confirm they pass again.

verified   The two non-store fixes are real and their downstream consequence is genuinely closed

TestAgentPhaseFailureErrorIsRedacted and TestDeliverPullRequestRedactsGHOutput both pass, and both genuinely exercise the fix rather than asserting a tautology: the first runs a fake failing agent script that echoes a secret and checks RunAgentPhase's returned error.Error(); the second runs a fake gh binary on PATH that echoes a secret-shaped warning line on its success path and checks DeliverPullRequest's return value. I additionally traced RunAgentPhase's fix to its actual consequence, since Review 016 specifically flagged this error as reaching os.Stderr from the CLI (the 8th instance, the most severe of the four Review 016 found): dag/engine.go:352–354 wraps the now-redacted error with %w, which preserves the already-substituted [REDACTED] text, and cmd/sergeant/main.go:116 prints that wrapped error verbatim. The 8th instance is closed at its source, not by a second patch at the print site.

residual, non-blocking, pre-existing   internal/graphify/graphify.go → handleBuildGraph still returns raw subprocess output in an HTTP response

BuildProjectGraph (internal/graphify/graphify.go, around lines 68 and 87) embeds the raw CombinedOutput of the external graphify extract/merge-graphs subprocess directly into a returned error with no redact call anywhere in the file. internal/ui/server.go's handleBuildGraph (around line 1604) returns that error verbatim via http.Error(w, err.Error(), http.StatusInternalServerError) — an HTTP response body carrying unredacted subprocess output. This is structurally outside anything the store choke point or the two runner fixes could ever catch, because this content never becomes a PhaseRecord, an EnvelopeRecord, or either of the two return values 9933725 fixed — it is a third, independent kind of write path (a direct HTTP error body) that this commit did not touch and was not trying to touch.

This is not a new discovery: Review 016 already disclosed this exact gap as a non-blocking residual, for the same reason it remains non-blocking now — the subprocess in question is sergeant's own graphify binary, not an arbitrary untrusted agent, so a real secret leak would require graphify itself to echo credential-shaped content (for example, a source line containing a hardcoded key, on a parse-failure message) rather than an agent intentionally or accidentally printing one. I did not construct a live reproduction with a real secret making it through graphify's own error formatting, so I am not escalating this from a disclosed residual to a confirmed leak. It remains open and unaddressed by this commit; a future review should either confirm it is unreachable in practice or fix it, but it does not undermine the choke-point claim under test here, which was specifically about PhaseRecord/EnvelopeRecord construction and the two named return-value paths.

verified   No second write path to either table, and no unreviewed production caller

Every non-test call to .RecordPhase( or .RecordEnvelope( in the internal/ tree resolves to one of four files (dag/engine.go, runner/runner.go, ui/server.go, mcp/server.go), and every one of those calls the Store method rather than raw SQL. The only production INSERT INTO phases/INSERT INTO envelopes statements in the entire repository live inside internal/store/store.go. The two other raw-SQL INSERT INTO envelopes hits are in internal/store/envelope_metadata_test.go, and reading the surrounding test confirms they exist specifically to bypass RecordEnvelope's validation and simulate a database row written before a schema migration — a deliberate test-only exception to prove the read path tolerates old rows, not a second production write path.

Verdict

MEETS SPEC. R4.4/R4.5 is now solid for this PRD cycle. The choke-point strategy is not just a relabeling of the same field-by-field pattern that produced nine misses across five commits and six review rounds — it is a genuine structural closure, and I verified that claim the only way that actually tests it: by finding two call sites that construct a PhaseRecord/EnvelopeRecord and were never reviewed, never wired to redact at the call site, and confirming a live secret embedded in each came out clean anyway, purely by passing through Store.RecordPhase/Store.RecordEnvelope. Both mutation tests confirm the redaction lines are load-bearing, not decorative. The two non-store fixes (RunAgentPhase's returned error, DeliverPullRequest's return value) are real, and I traced the more severe of the two — the CLI-stderr leak Review 016 flagged as an explicit "log" violation of R4.4's own wording — to confirm it is closed at its source rather than merely at the function that changed. The full suite is clean and every field on both record structs was checked, not only the fields the shipped tests exercise.

One residual gap remains, and it is disclosed here rather than treated as blocking: internal/graphify/graphify.go's raw subprocess output can still reach handleBuildGraph's HTTP error response unredacted. This is not new — Review 016 already named it — and this commit did not touch it because it is structurally a different kind of leak than the one 9933725 was built to close: it never becomes a PhaseRecord, an EnvelopeRecord, or a value RunAgentPhase/DeliverPullRequest return, so no choke point downstream of those functions could ever catch it. It is lower-likelihood than the nine prior instances (the subprocess is sergeant's own binary, not an arbitrary agent) and was not independently reproduced with a live secret in this review, so it stands as a disclosed residual, not a blocker on this verdict.

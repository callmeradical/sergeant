This matches all four scenarios in specs/blocked-bullets/spec.md at the mapping level: agent-reported reason, synthesized reason, passing run unaffected, cancelled run moves nothing.

verified   The reason lives inside payload, not a new top-level field, exactly as design.md requires

handoff.BlockedReason(payload json.RawMessage) string is a pure map lookup: json.Unmarshal into map[string]interface{}, return fields["blocked_reason"] if present and a string, else "". The Envelope struct itself gained no new field. Design.md's stated reason for this choice — inheriting redact.JSON's existing call site instead of needing a new one — is real, not just asserted: I traced the actual redaction call in RunAgentPhase and confirmed the read happens strictly after it (next finding).

verified   Redaction-then-read ordering is correct in the one place it's claimed, and doubly enforced

internal/runner/runner.go line 495: env.Payload = redact.JSON(env.Payload). Line 504: blockedReason := handoff.BlockedReason(env.Payload). The comment directly above line 504 states this ordering is deliberate, and the code matches the comment. Line 506's annotatePayloadWithProvenance then re-unmarshals/re-marshals the same payload to add model/provider keys — I checked this preserves blocked_reason rather than dropping it, since it round-trips through the same map[string]interface{} shape. Separately, internal/store/store.go's RecordEnvelope (the choke point Review 018 examined) unconditionally redacts e.Data again before INSERT, so blockedReasonForRun's read-back through ListEnvelopesForRun is protected even if the runner-level ordering were ever broken by a future edit. Two independent redaction passes on the same field, not one fragile one.

verified   This really is a full replacement, not a parallel or inconsistent write path

Grepped every "failed" string literal and every UpdateBulletStatus/AdvanceBulletsForRun call site in internal/, excluding tests. bulletStatusForRunOutcome (called only from recordTerminalRun, called only from the run-completion path) is the sole place that ever computed a bullet status from a run outcome, both before and after this commit. The plan-approval path added later (server.go:863) only ever writes "pending" for a freshly approved bullet and is unreachable from a run outcome, so it cannot reintroduce a stray "failed" write. Historical rows keep "failed" (no migration was written, matching the proposal's explicit out-of-scope item), and BulletStatuses() documents both values.

real gap, pre-existing in internal/redact, inherited by this feature   A credential-shaped blocked_reason embedded mid-sentence is not redacted

I wrote a throwaway test driving two different secret shapes through the real end-to-end path (RecordEnvelope → srv.recordTerminalRun → ListBulletsForIntent), neither of which the shipped tests used: a GitHub personal-access-token shape (ghp_...) and an inline PASSWORD=... credential, both inside one blocked_reason string: "pushed with token ghp_ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789 and PASSWORD=hunter2superSecret failed auth". The persisted BulletRecord.BlockedReason came back as "pushed with token [REDACTED] and PASSWORD=hunter2superSecret failed auth" — the GitHub token was redacted; the password was not.

I isolated this to internal/redact/redact.go itself, with no ui/runner/store code involved: credentialLinePattern is (?im)^([A-Za-z0-9_.-]*(?:key|token|secret|password|credential)[A-Za-z0-9_.-]*)=(.+)$. The ^/$ anchors (multiline mode) require the credential to start its own line. redact.Text("PASSWORD=hunter2superSecret") alone on a line redacts correctly to "PASSWORD=[REDACTED]"; the identical text embedded mid-sentence does not match, because there is no line break immediately before PASSWORD. apiKeyPattern (the pattern that caught the GitHub token) has no such anchor and matches anywhere in the string, which is why that half of the same probe came back clean.

This is not a defect this commit introduced. Review 018 (bd58bd4) already disclosed a sibling case — a generic credential embedded in a URL's userinfo — for the identical underlying reason: no redact.go pattern matches it. Design.md's own rationale for nesting blocked_reason inside payload is to inherit the existing, already-tested redaction wiring "for free" instead of adding a new call site — and that choice is sound engineering (a new call site is where redaction gaps have historically been introduced in this project, per Reviews 013–018's history of finding exactly that). But "inherits the existing wiring" necessarily also means "inherits the existing wiring's blind spots," and an agent's own free-text explanation of why it is stuck is a plausible place for a credential to appear mid-sentence rather than helpfully alone on its own line. R4.4's spec text for this change says a blocked reason must be "redacted like any other retained free text" — which is true here in the literal sense (it goes through the exact same redact.Text as everything else), but the underlying heuristic that "like any other" points to has a known scope limit that a human-facing dashboard reason string now inherits.

Verdict

MEETS SPEC WITH CAVEATS. Every scenario in specs/blocked-bullets/spec.md is genuinely implemented: bulletStatusForRunOutcome's "failed" case now yields "blocked" with "passed" and cancelled/default left untouched; an agent-reported reason is threaded through verbatim from payload.blocked_reason (not a new top-level Envelope field, matching design.md's explicit rejection of that alternative); a run with no agent-reported reason still produces a non-empty synthesized one; and the reason is redacted through the existing, already-tested redact.JSON/RecordEnvelope wiring rather than a new call site. The mutation test confirms the core replacement is load-bearing, not decorative — reverting one line breaks 4 tests in exactly the predicted way, and the fix restores to an empty git diff. The whole-repo grep confirms this really is a full replacement: no other code path writes a bullet's status from a run outcome. Test quality is genuinely good: reason assertions check the exact verbatim string, and redaction assertions check both the specific secret's absence and the specific placeholder's presence, matching the bar the project's own redaction suite holds itself to. go build, go vet, and go test ./internal/... -count=1 all pass clean at current HEAD.

The caveat is what I found doing my own independent redaction probe (task item 8), using secret shapes the shipped tests did not use. A GitHub-token-shaped (ghp_...) secret inside an agent-reported blocked_reason is redacted correctly end-to-end into BulletRecord.BlockedReason. A PASSWORD=...-shaped credential embedded mid-sentence in the same field is not — it is retained verbatim, because internal/redact's credentialLinePattern only matches a credential that starts its own line, and an agent's free-text explanation of why it is stuck has no reason to format itself that way. I traced this to internal/redact/redact.go directly, with no code from this commit involved, and confirmed via Review 018 (bd58bd4, an unrelated commit) that this is a known, pre-existing scope limit of the heuristic, not something fcc28fd introduced.

I am not calling this a blocker, for the same reason design.md gives for the architectural choice in the first place: reusing an existing, already-tested redaction call site is the right call, and the alternative (a bespoke redaction pass for just this one field) is exactly the "new field, new call site, easy to forget" shape that produced this project's worst redaction gaps historically (Reviews 013–018). But R4.4's spec text for this change — "redacted like any other retained free text" — is true in the narrow sense (it goes through the same function as everything else) while still leaving a real, reachable gap in the broader sense a reader would reasonably assume: not every credential-shaped substring in a blocked reason is actually caught. This is a caveat on the redaction guarantee this feature relies on, not on the feature's own logic, which is correctly wired and correctly tested for what it does control.

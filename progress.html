Findings

verified   b2c157d's own fix is real: summary and payload are genuinely redacted

redact.Text(summary) and redact.JSON(payloadBytes) sit directly in the field assignments of the EnvelopeRecord literal, not conditionally, not behind a flag. The shipped test (TestEmitEnvelopeRedactsAgentSuppliedContent) passes and genuinely exercises both fields with a secret nested two levels deep in payload. I did not stop at reading the diff: I reverted both calls back to the raw pre-fix values, reran the test, and it failed on all 4 of its assertions (returned tool text, persisted Summary, persisted Data twice — once for leak, once for missing placeholder) with the secret visible in every failure message. I then restored the file exactly via git checkout -- and confirmed git diff/git status --short were both empty before rerunning the test to confirm it passes again. This specific fix is load-bearing, not decorative.

bad   Sixth instance: sergeant_emit_envelope's own third field, artifacts, is still unredacted

The same MCP tool call that b2c157d just fixed takes three pieces of agent-supplied content: summary, payload, and artifacts. Only the first two were wired to redact:

var artifacts []string
if rawArt, ok := args["artifacts"].([]interface{}); ok {
    for _, a := range rawArt {
        if s, ok := a.(string); ok {
            artifacts = append(artifacts, s)   // no redact.Text anywhere
        }
    }
}
...
Artifacts:     artifacts,   // stored verbatim

I confirmed this is a real, reproducible leak: calling sergeant_emit_envelope with artifacts: ["API_KEY="+secret] persists that exact string, unredacted, into EnvelopeRecord.Artifacts. This is the closest possible miss to the fix that was just shipped — a third field on the exact same struct literal, in the exact same commit's own diff, one line above and one line below the two that were fixed.

persisted EnvelopeRecord.Artifacts = ["API_KEY=sk-abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOP"]

bad   Seventh instance: the same Artifacts gap already existed in the original runner path, unnoticed across three prior reviews

RunAgentPhase's agent-authored-envelope branch — the exact branch 3c95c1b fixed for Summary/Payload, and the exact branch Review 015 mutation-tested — populates env directly from an agent-written .sergeant/envelope.json via json.Unmarshal. Lines 481–482 then redact env.Summary and env.Payload unconditionally, but env.Artifacts []string (from internal/handoff/envelope.go) is never touched before it reaches RecordEnvelope at line 507. An agent that writes its own envelope with a secret inside the artifacts array — plausible, since artifacts are exported paths or references an agent names itself — persists that secret verbatim. I reproduced this directly: a fake agent script writes .sergeant/envelope.json with "artifacts":["API_KEY="+secret], exits 0, and both the returned envelope and the persisted EnvelopeRecord.Artifacts carry the raw secret:

returned envelope Artifacts leaked the secret: [API_KEY=sk-abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOP]
persisted EnvelopeRecord.Artifacts leaked the secret: [API_KEY=sk-abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOP]

This gap predates b2c157d entirely — it was sitting in the exact code Reviews 014 and 015 both examined line-by-line, and the exact code Review 015's own mutation test touched, without being noticed. It is the same root cause as the sixth instance above: Artifacts is never wired to redact anywhere in this codebase, in either of the two independent places an agent can populate an envelope.

bad   Eighth instance: RunAgentPhase's failure-path error leaks raw agent output straight to a terminal

This is the exact "second independent raw read of the buffer" bug already fixed twice — once in RunCodeGate (3d09f7a), once conceptually in handleCreatePR (3d09f7a) — recurring a third time, in a third function, in the same file RunCodeGate's fix lives in:

if failed {
    lastErr = fmt.Errorf("%s (output: %s)", failureReason, stripANSI(strings.TrimSpace(outBuf.String())))
    ...
}

outBuf is the agent subprocess's raw combined stdout/stderr. Three lines above, the same buffer is correctly redacted and bounded into the synthesized envelope's raw_output field (redact.Truncate(redact.Text(stripANSI(outBuf.String())), maxRawOutputBytes) at line 467). The lastErr construction at line 556 reads the identical buffer a second time with none of that applied. This error is not just an internal detail: I traced its full call chain. dag/engine.go:352–355 wraps it and returns it from RunStage. The web-dispatch path (internal/ui/server.go) discards the text and only persists a status string, so a run started from the dashboard is safe. But cmd/sergeant/main.go's sergeant run <project> command — the CLI entry point — prints it verbatim to the terminal:

if err := engine.RunStage(ctx, taskID, &stage); err != nil {
    fmt.Fprintf(os.Stderr, "❌ Stage %s failed: %v\n", stage.Name, err)

I reproduced this directly: a fake agent script that echoes API_KEY=<secret> and exits 1 produces an error whose .Error() string contains the raw, unredacted secret:

err.Error() == "agent .../agent.sh exited with error: exit status 1 (output: API_KEY=sk-abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOP)"

R4.4 explicitly names "logs" alongside records/responses/notifications. A CLI printing a raw secret to stderr on a failing agent phase is exactly that.

bad   Ninth instance: sergeant_seal_pr — the second MCP tool the task named — returns raw gh output unredacted

The task specifically asked me to check sergeant_seal_pr alongside sergeant_emit_envelope. It calls PhaseRunner.DeliverPullRequest (internal/runner/runner.go:574–614), a function distinct from internal/ui/server.go's handleCreatePR — the function 3d09f7a actually fixed. grep -n "redact\." internal/runner/runner.go shows every redact call site in the file; none are in or near DeliverPullRequest. Its success path returns the raw subprocess buffer directly:

if err := cmd.Run(); err != nil {
    ... // failure path: returns a hardcoded string, does not leak `out`
}
return strings.TrimSpace(out.String()), nil   // success path: raw, unredacted

This return value flows straight back as the MCP tool's response text (internal/mcp/server.go:424–428, sergeant_seal_pr case). I reproduced this directly with a fake gh binary on PATH that exits 0 (the success branch) while echoing a secret-shaped string to stdout — the kind of thing a real gh can emit as a warning even on a technically-successful invocation (e.g. a stale-credential notice):

DeliverPullRequest returned: "warning: using cached credential sk-abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOP"

This is a third, wholly independent write/return path for gh's output — after handleCreatePR (fixed) and unrelated to it — that none of the four prior fix commits in this lineage ever touched, because none of them looked at internal/mcp/server.go's sergeant_seal_pr case until this review.

Not independently reproduced with a live failure.

resolveGitRemoteURL (internal/ui/server.go:575–596): a remote URL with inline userinfo (https://user:token@host/repo.git) does not match the special-cased github.com/ prefix and falls through to the generic http(s):// branch, which strips only the .git suffix and returns the URL — credentials intact — into EnvelopeRecord.Data/Artifacts via both handleCreatePR and describeDelivery. This requires an operator to have configured a git remote with inline credentials, which is an unusual (if not unheard-of) local setup rather than agent-controlled input; it is a genuine R4.4-shaped gap but a different threat model than the rest of this review chain, and I did not construct a live reproduction.

Neither is blocking on its own. Both are named here so they are not rediscovered as a surprise later.

Verdict

DOES NOT MEET SPEC. b2c157d's own claim is genuine and verified: summary and payload in sergeant_emit_envelope are correctly redacted, and the fix is load-bearing under mutation testing. But this review round was explicitly asked to do one final exhaustive sweep given the pattern had already recurred five times, and it found four more concrete, independently reproduced leaks — not theoretical concerns, each backed by an exact input that produces an exact unredacted secret in a persisted record, a CLI log line, or an MCP tool response:

  • Blocking: sergeant_emit_envelope's artifacts field — the third agent-supplied field on the exact tool call this commit just fixed two of three fields on — is still stored unredacted.
  • Blocking: the identical Artifacts gap already existed, pre-b2c157d, in RunAgentPhase's agent-authored-envelope branch — the same branch three prior reviews (014, 015, and this one) have now read line-by-line without anyone noticing Artifacts was never wired to redact at all, in either of the two independent places an agent can populate one.
  • Blocking: RunAgentPhase's failure-path error is a third occurrence of the "second independent raw buffer read bypasses redaction" bug already fixed twice in this exact lineage (RunCodeGate, handleCreatePR), and it is the most severe of the four: it reaches os.Stderr directly from the CLI's main run command, an explicit "log" under R4.4's own wording.
  • Blocking: sergeant_seal_pr — the second MCP tool the task named for inspection — calls a function (DeliverPullRequest) with zero redact references anywhere in it, returning raw gh pr create subprocess output as the tool's response text on success.

Two further, lower-severity paths (graphify subprocess output reaching an HTTP error response; resolveGitRemoteURL carrying inline git credentials into a record if an operator's remote is configured that way) are disclosed as non-blocking residuals — different threat models, lower likelihood, not independently reproduced — rather than treated as part of this verdict's blocking set.

This makes nine total instances of the same underlying failure mode across five fix commits, and the rate of discovery has not slowed: every review round that has exhaustively swept call sites, rather than trusting the previous round's list was complete, has found something the previous round missed. A sixth fix round is warranted, and given the density of remaining gaps, the next round should not fix these four in isolation — it should establish a single, structural guarantee (e.g. a constructor or wrapper type for EnvelopeRecord/PhaseRecord that redacts every string-bearing field, including Artifacts, before a caller can construct one at all, and an equivalent guarantee for any error value built from raw subprocess/agent output before it can be wrapped and returned) rather than another field-by-field patch, since field-by-field patches are exactly what has produced nine misses in a row.

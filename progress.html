Findings

verified   Gap 1 (AKIA/AIza glued-suffix miss) is genuinely fixed

The new pattern drops the trailing \b and changes the fixed repetition counts ({16}/{35}) to open-ended floors ({16,}/{35,}), exactly as the commit message describes and exactly matching the shape the other five prefixes already used. I reran Review 014's precise reproduction myself rather than trusting the shipped test: Text("AKIAIOSFODNN7EXAMPLEXTRACHARS") now returns "[REDACTED]" — the full key no longer leaks. The Google-key case behaves the same way. The two new tests in redact_test.go (TestTextRedactsProviderKeysGluedToTrailingText) assert the same pairing this codebase's history already established as the right one: secret absent and placeholder present, not a generic truthiness check.

verified   Gap 1 edge cases: no new data loss, one cosmetic over-match

I tried inputs not in the shipped suite. Two AKIA-shaped keys glued together with no separator ("AKIAIOSFODNN7EXAMPLEAKIAIOSFODNN7EXAMPLE2") collapse into a single [REDACTED] rather than two — the greedy {16,} floor consumes both keys as one run of [A-Z0-9] characters, since the embedded AKIA text is itself valid [A-Z0-9]. This is over-matching, not a leak: no byte of either key survives in the output. It is also the exact tradeoff the code's own doc comment accepts ("the rare over-match ... risks" is preferred to a silent miss), so this is not a regression, just a confirmation the tradeoff is real and does not go further than advertised. Two keys separated by a single space redact independently and correctly ("[REDACTED] [REDACTED]"). A key glued to underscore-joined trailing text ("AKIAIOSFODNN7EXAMPLE_LOOKS_LIKE_MORE_KEY_DATA_HERE") redacts only up to the underscore, which is correct — the underscore is not part of the key's own character class, so nothing past it was ever part of the real secret. An under-floor string ("AKIA1234", 4 chars after the prefix) is correctly left untouched, matching the pre-existing 16/35-char minimum-length design.

verified   Gap 2 (agent-envelope redaction bypass) is genuinely fixed, on both branches

env.Summary = redact.Text(env.Summary) and env.Payload = redact.JSON(env.Payload) sit immediately after the if/else that builds env, with no branch-specific conditional around them — so both the agent-authored-envelope branch (os.ReadFile succeeds) and the synthesized-envelope branch (the else) pass through both calls. This closes the gap the way the commit message claims: "a future third envelope-construction path can't reintroduce the same gap by omission" is accurate, since the calls are keyed to the shared env variable after the branch, not duplicated inside each branch. TestAgentAuthoredEnvelopeIsRedacted genuinely exercises the previously-broken branch (a fake agent script writes .sergeant/envelope.json itself) and checks the returned envelope, PhaseRecord.Payload, and EnvelopeRecord.Data — I read ListPhasesForRun/ListEnvelopesForRun myself rather than trusting the test file's own assertions, and the persisted rows are genuinely clean.

verified   Gap 2 holds at a nested-array depth not covered by the shipped test

The shipped TestJSONRedactsStringLeavesAtAnyDepth covers a top-level string, a map-nested string, and an array element, but not a string nested inside an object that is itself an element of an array (a shape a real agent's structured findings would plausibly use). I wrote my own reproduction: payload.findings[0].note holding a secret, with findings itself an array mixing an object and a plain string. The result redacted correctly at every level:

persisted EnvelopeRecord.Data = {"findings":[{"note":"leaked [REDACTED]"},"ordinary"],"model":"","provider":""}

The plain-string array element ("ordinary") survived untouched, confirming redactValue's recursion does not over-redact non-secret content at any depth.

bad   A third call site in the same family: RunCodeGate's PhaseRecord.Error leaks raw, unredacted, unbounded gate output on failure

RunCodeGate (runner.go, ~line 259–276) builds errStr only when the gate command fails:

if !passed {
    status = "failed"
    if err != nil {
        errStr = fmt.Sprintf("%v: %s", err, outBuf.String())
    }
}
...
phaseRec := &store.PhaseRecord{
    ...
    Error:      errStr,
    ...
}

outBuf.String() here is the raw command output — the same buffer that, three lines earlier, is correctly passed through redact.Truncate(redact.Text(stripANSI(outBuf.String())), maxRawOutputBytes) to build cleaned/result.Output. errStr is built from the same buffer a second time, independently, with none of that processing applied — no redact.Text, no redact.Truncate, no stripANSI. It is then stored directly into PhaseRecord.Error, a field the store persists and the API/dashboard exposes (store.PhaseRecord.Error string \`json:"error,omitempty"\`). This is exactly the same shape of bug as both of Review 014's findings and this commit's own fix: a codepath sergeant did not build field-by-field for the "safe" field, so it never received the same treatment as its sibling. The existing test, TestRunCodeGateRedactsSecretsFromPersistedRecords, cannot catch this: its gate command is "echo 'AWS_CREDENTIAL="+secret+"'" with no exit 1, so the gate always passes and errStr is never populated in that test at all.

I confirmed this is a real, reproducible leak with a throwaway test (a gate command that echoes a secret and then exits non-zero, exactly the shape of a test suite or lint tool that dumps an environment variable in its failure output):

res, _ := pr.RunCodeGate(ctx, "failing-gate", "echo 'AWS_CREDENTIAL="+secret+"'; exit 1")
phases, _ := st.ListPhasesForRun("run-1")
// phases[0].Error == "exit status 1: AWS_CREDENTIAL=AKIAIOSFODNN7EXAMPLE\n"
//                     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ raw secret, unredacted, unbounded

Unlike result.Output, errStr is also never truncated — a failing gate that produces megabytes of output before exiting non-zero would persist all of it into PhaseRecord.Error with no maxRawOutputBytes bound at all, which is the same unbounded-storage risk R4.5 already named and fixed for the sibling field.

weaker instance, same family   internal/ui/server.go's create-PR envelope embeds raw gh subprocess output unredacted

handleCreatePR calls srv.GHPRCreate (default implementation runGHPRCreate, cmd.CombinedOutput() of a real gh pr create subprocess). On failure, prError := strings.TrimSpace(string(out)) is embedded directly into EnvelopeRecord.Data via fmt.Sprintf(...%q...), with no call to redact.Text anywhere — I confirmed internal/ui/server.go has zero references to the redact package at all. This is a weaker finding than the RunCodeGate one: gh CLI error output is less likely than a project's own test/lint output to echo a credential, and I did not construct a live reproduction (doing so would require a real or faked gh binary). I'm flagging it because it fits the same provenance shape the task asked me to check for — durable content originating from an external process, not synthesized by sergeant — and because gh failures routinely include the value of malformed --body/--title arguments or auth diagnostics that can carry a token in less common configurations (e.g. a misconfigured GH_TOKEN echoed in an error). Non-blocking on its own, but it belongs on the same list as the RunCodeGate.Error finding above rather than being treated as a one-off.

verified   Scope discipline held

The commit touches exactly 4 files (2 source, 2 test), all under internal/redact and internal/runner. No config field was added for either fix. annotatePayloadWithProvenance is unchanged and still runs after the new redact calls, so provenance metadata (model/provider) is added to an already-redacted payload rather than the other way around — the ordering is correct, since provenance values are not secret-shaped and redacting them would be meaningless, but it does mean a provenance annotation added after redaction is never itself scanned; I checked and model/provider values come only from detectModelProvider's own regex capture groups against a fixed banner shape, not from arbitrary agent-controlled text, so this is not a gap.

Verdict

MEETS SPEC WITH CAVEATS. Both gaps Review 014 identified are genuinely, independently verified as fixed. Gap 1 (AKIA/AIza glued-suffix miss): I reran Review 014's exact reproduction myself and it now redacts correctly, and I could not find any new leak in several edge cases beyond the shipped test suite — the only surprising behavior (two glued keys collapsing into one placeholder) is a benign over-match, not a data loss, and matches the code's own documented tradeoff. Gap 2 (agent-authored-envelope bypass): the two new redact calls in RunAgentPhase run unconditionally after either envelope-construction branch, so both the previously-broken branch and the always-correct branch are covered; I verified this holds at a nested-array depth the shipped test does not exercise, checked the actual persisted PhaseRecord/EnvelopeRecord rows myself rather than trusting the test file's assertions, and confirmed the fix is load-bearing by reverting it, watching the shipped test fail on all five of its assertions, and restoring the exact original text.

The caveat is a third instance of the exact same failure pattern, found by doing what Review 014's own text warned would be necessary: exhaustively tracing every RecordPhase/RecordEnvelope call site rather than assuming the two known gaps were the only ones. RunCodeGate builds its result.Output field correctly, through redact.Truncate(redact.Text(stripANSI(...)), maxRawOutputBytes) — but on gate failure it independently rebuilds an errStr from the same raw output buffer a second time, with none of that processing applied, and persists it verbatim and unbounded into PhaseRecord.Error. I reproduced this directly: a failing gate command that echoes a secret leaves that secret, in full, in the store. A fourth, weaker instance sits in internal/ui/server.go's create-PR handler, which embeds raw gh pr create subprocess output into EnvelopeRecord.Data with zero references to the redact package anywhere in that file — not independently reproduced with a live failure, but the same provenance shape (external process output reaching a durable record unfiltered) the task asked to be checked for. This exact "wired only some call sites, not the sibling field/file" pattern has now recurred three times across two consecutive reviews of this one bullet's lineage, which suggests the underlying risk is systemic rather than incidental: any future redaction fix in this codebase should be paired with an exhaustive RecordPhase/RecordEnvelope grep across the whole binary, not just the file the previous finding lived in.
